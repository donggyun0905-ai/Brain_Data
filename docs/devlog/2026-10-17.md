# 2026-10-17 — 개발 PC에 Docker 구성, Flink 첫 실행. 워터마크가 조용히 무시되는 문제 발견

> 그날 나온 ADR: 0006(개발 PC와 AWS) · 0007(소스 워터마크)
>
> 이 파일은 ADR-0006·0007, `docs/week1.md`, 그리고 `flink_jobs/watermarks.py`·
> `docker-compose.local.yml` 코드를 근거로 정리했다 (일지 체계를 2026-10-19에 만들었기 때문에
> 실시간 기록은 없다).

## 0. 이 날 한 일
어제는 숫자로만 결정했고, 이 날 처음 **실제로 띄웠다.** 그러자 종이에서 안 보이던 것들이 나왔다.

1. 메모리가 모자라 core 묶음을 그대로 띄울 수 없었다 → PC용 가벼운 설정 (ADR-0006)
2. Flink 이미지가 빌드에서 두 번 실패했다 → Dockerfile 수정
3. **집계가 거의 다 틀렸다.** 원인은 워터마크였고, PyFlink가 시각 추출기를 **오류 없이 무시**하고
   있었다 (ADR-0007)

3번이 이 날의 본체다. "데이터는 다 읽었는데 집계에서 빠진다"는 가장 찾기 어려운 종류의 버그다.

## 1. 메모리가 모자랐다 (ADR-0006)

### 1-1. 무엇이 틀렸나
기획서는 개발을 개인 노트북(0원)에서 하고 core 묶음(약 9GB)이 돈다고 가정했다.
실제 개발 PC는 메모리 15.4GB, Docker(WSL2) 할당 8GB이고 **core의 메모리 한도 합은 약 11GB**였다.
PyCharm과 브라우저를 함께 쓰면 띄울 수 없다.

### 1-2. 후보와 선택
| 방식 | 판정 |
| --- | --- |
| WSL 메모리 할당을 12GB 이상으로 늘림 | 탈락. Windows·PyCharm·브라우저 몫이 3GB대로 줄어 개발이 느려짐 |
| 처음부터 EC2에서 개발 | 보류. 상시 켜두면 예산을 빨리 씀 |
| 관리형 서비스(MSK, Managed Flink) | 탈락. 예산 초과, 설계 원칙 10 |
| **PC는 가벼운 덮어쓰기 설정, 실험은 EC2 스팟** | **채택** |

### 1-3. 어떻게 나눴나
기본 `docker-compose.yml`은 **실험 장비(AWS 32GB) 기준으로 그대로 두고**, PC에서는 겹쳐 쓰는
파일을 따로 만들었다.

```yaml
# docker-compose.local.yml — 개발 PC용 가벼운 설정 (ADR-0006)
services:
  kafka:
    environment:
      KAFKA_HEAP_OPTS: "-Xms256m -Xmx512m"
    mem_limit: 900m
  jobmanager:
    environment:
      FLINK_PROPERTIES: |
        jobmanager.rpc.address: jobmanager
        jobmanager.memory.process.size: 900m
        metrics.fetcher.update-interval: 1s
    mem_limit: 1100m
  taskmanager:
    deploy: { replicas: 1 }      # 기본은 2개
    ...
```

```bash
docker compose -f docker-compose.yml -f docker-compose.local.yml --profile core up -d \
  kafka kafka-init jobmanager taskmanager
```

**왜 기본 파일을 줄이지 않았나**: 같은 파일을 EC2에서 쓴다. 기본값이 PC에 맞춰져 있으면
실험 장비에서 성능이 안 나와도 원인을 알기 어렵다. **"기본은 실험 장비, 덮어쓰기는 개발 PC"**가
숫자를 해석할 때 혼동을 막는다.

### 1-4. 함께 고친 것
기본 설정의 JobManager 메모리가 **이미지 기본값 1,600MB**인데 컨테이너 한도가 1,500MB여서
그대로는 시작하지 못했다 → 1,200MB로 명시했다. 가벼운 설정에서는 900MB.

### 1-5. 숫자 해석 규칙을 정했다
> PC에서 잰 처리량은 **기능 확인용으로만** 쓰고, E1 기준선 같은 실험 수치는 실험 장비에서만 잰다.

이 규칙이 뒤에 계속 인용된다. 2026-10-19에 처리 능력 실측치 687이 나왔을 때도 이 규칙 때문에
"확정값이 아니다"로 적었다.

## 2. Flink 이미지 빌드 실패 2건

`infra/flink/Dockerfile`이 두 번 실패했다. 둘 다 "로컬에서 상상한 것과 컨테이너 안이 다른" 경우다.

| 실패 | 원인 | 고침 |
| --- | --- | --- |
| `apt-get` 권한 없음 | `flink` 이미지의 기본 사용자가 `flink`라 apt를 쓸 수 없다 | 설치 동안만 `USER root` |
| 가상환경이 안 잡힘 | `/usr/bin/python` 심볼릭 링크로는 venv가 활성화되지 않는다 | `PATH`에 `/opt/venv/bin` 추가 |

그리고 커넥터 버전이 틀렸다.
```
flink-sql-connector-kafka  4.0.1-2.0   (Flink 2.0용)   ← 처음
                        →  5.0.0-2.2   (Flink 2.2용)   ← 고침
```

확인한 사실: `flink:2.2.1-java17` 태그 존재, 기반 OS Ubuntu 24.04, 그 안 `python3` = **3.12.3**
(어제 정한 Python 3.12 고정과 맞는다).

## 3. 이 날의 본체 — 집계가 거의 다 틀렸다 (ADR-0007)

### 3-1. 증상
가짜 데이터(REES46 형식, 10분, 2,020건)를 Kafka에 **먼저 다 넣고** Flink 작업을 **나중에** 띄워
밀린 데이터를 따라잡게 했다. 그러자 메인 작업의 1분 집계가 정답과 크게 달랐다.

> **닫힌 창 70개 중 대부분이 틀림. 밀림은 0이라 데이터는 다 읽었는데 집계에서 빠짐.**

"다 읽었는데 집계에 없다"는 워터마크 문제의 전형적인 모습이다. 이벤트가 '늦음'으로 판정되어
이미 닫힌 창에 들어가지 못하고 버려진 것이다.

그리고 이 장면은 **이 프로젝트의 핵심 장면**이다. 폭증 때 밀렸다가 따라잡는 것이 바로
우리가 보여 주려는 상황이다. 여기서 틀리면 프로젝트가 성립하지 않는다.

### 3-2. 원인 1 — 워터마크를 붙이는 자리가 틀렸다
처음 코드는 Kafka에서 읽은 **뒤** 합친 흐름에 워터마크를 붙였다.

```python
# 틀린 구조
kept = (view.union(cart).connect(control).process(SheddingFilter())
        .map(to_record)
        .assign_timestamps_and_watermarks(          # ← 합친 뒤에 붙임
            WatermarkStrategy.for_bounded_out_of_orderness(Duration.of_seconds(5))
            .with_idleness(Duration.of_seconds(10))
            .with_timestamp_assigner(EventTime())))
```

밀린 데이터를 읽을 때 Kafka 리더는 **파티션 하나를 몇 분치씩 몰아 읽는다.** 그러면 합친 흐름의
시각이 뒤섞이고, 앞서 나간 워터마크 때문에 다른 파티션의 이벤트가 '늦음'으로 버려진다.

워터마크는 **파티션별로** 만들어야 한다. 그래야 "파티션 A는 14:05까지, 파티션 B는 14:01까지
읽었으니 전체 기준선은 14:01"이라는 판단이 된다.

### 3-3. 원인 2 — PyFlink가 시각 추출기를 조용히 무시한다
파티션별로 만들려면 소스에 워터마크 전략을 넘겨야 한다. 그런데:

> 소스에 넘긴 Python `TimestampAssigner`는 PyFlink 2.2.1 `from_source`에서 **오류 없이 무시**된다.
> 워터마크가 2019년이 아니라 Kafka 기록 시각(2026-10-17)으로 잡히는 것을 REST API로 확인했다.

**예외도, 경고도 없다.** 작업은 정상으로 보이고 숫자만 틀린다. REST API로 워터마크 값을 직접
들여다봐서야 알았다.

> 어제(10-16) "`WatermarkStrategy.with_idleness`가 있음"을 확인했는데, **있는 것과 동작하는 것이
> 달랐다.** 이 경험이 10-16 일지의 교훈 4번이 됐다.

### 3-4. 후보 비교
| 방식 | 판정 |
| --- | --- |
| 합친 흐름에 워터마크 (기존) | 탈락. 따라잡기 중 데이터 손실 |
| `from_source` + Python 시각 추출기 | 탈락. **PyFlink가 추출기를 무시함** |
| Kafka 기록 시각을 이벤트 시각(2019년)으로 보냄 | 탈락. **7일 보관 규칙이 즉시 지움** (설계 원칙 7과 충돌) |
| 소스 병렬도를 파티션 수만큼 올리고 소스 직후에 워터마크 | 탈락. 조회 토픽 12칸 → 메모리 부족 |
| **Flink SQL Kafka 소스에서 머리말의 `event_ms`로 `WATERMARK` 선언 → `to_data_stream`** | **채택** |

세 번째 후보가 특히 배울 점이다. "Kafka 기록 시각을 2019년으로 맞추면 워터마크가 저절로
맞지 않나?"는 그럴듯하지만, **7일 보관 규칙이 2019년 메시지를 즉시 지운다.** 설계 원칙 7
("걸러진 데이터도 버리지 않는다")과 정면으로 충돌한다. 한 문제를 고치려다 다른 원칙을 깨는 경우다.

### 3-5. 채택한 방식
머리말에 `event_ms`를 추가해 **본문을 파싱하지 않고도** 이벤트 시각을 꺼낼 수 있게 했다.

```
user_id \t event_id \t event_ms \t ingest_ms \t {본문 JSON}
                       ^^^^^^^^ 추가 (ADR-0005 보완)
```

그리고 Flink SQL 쪽에서 계산 열로 꺼내 워터마크를 선언한다.

```python
# src/databrain/flink_jobs/watermarks.py
def event_source(t_env, bootstrap, topic, group, name):
    event_ms = f"CAST(SPLIT_INDEX(`v`, '{TAB}', 2) AS BIGINT)"
    t_env.execute_sql(f"""
        CREATE TEMPORARY TABLE `{name}` (
            `v` STRING,
            `ts` AS TO_TIMESTAMP_LTZ({event_ms}, 3),
            WATERMARK FOR `ts` AS `ts` - INTERVAL '{OUT_OF_ORDER_S}' SECOND
        ) WITH (
            'connector' = 'kafka',
            'topic' = '{topic}',
            'scan.startup.mode' = 'earliest-offset',
            'value.format' = 'raw'
        )""")
    return t_env.to_data_stream(t_env.from_path(name)).map(lambda r: r[0], output_type=Types.STRING())
```

**왜 이게 되는가**: 워터마크 계산이 **Java 쪽에서 파티션별로** 일어난다. Python 함수를 거치지
않으므로 무시될 일이 없고, Python 호출 비용도 없다. 이벤트 시각과 워터마크는 `to_data_stream`으로
DataStream에 그대로 넘어온다.

### 3-6. 제어 토픽은 따로 다뤘다
```python
def control_source(env, bootstrap, group):
    src = (KafkaSource.builder()...build())
    return env.from_source(src, WatermarkStrategy.no_watermarks().with_idleness(CONTROL_IDLE), "control")
```

제어 토픽(`control.rates`)은 **워터마크를 내지 않고 0.5초 유휴 시간만** 둔다. Flink는 연결된
입력 중 **가장 느린 기준선**을 따르기 때문에:

- 기준선을 계속 내지 않으면 → 집계 창이 **영영 닫히지 않는다**
- 현재 시각(2026년)을 내면 → 재생 중인 2019년 데이터가 **전부 '늦음'으로 버려진다**

그래서 "기준선 없음 + 짧은 유휴 시간"이다. 메시지가 올 때만 잠깐 활성이 되고 곧 유휴로 빠진다.

### 3-7. 고친 뒤 확인
```
따라잡기 상황: 메인 70/70, 구매 19/19 창이 DuckDB 정답과 일치
조회 비율 30% 신호 + 2만 건 재생: 조회 29.7% 통과, 1/비율 추정 오차 -0.9%,
                                  장바구니 100%, 빠진 창 0
```

가짜 데이터로 1회 확인이고, 실제 데이터 3회 반복은 다음 날로 넘겼다
(→ 2026-10-18에 실시간 3회·따라잡기 3회 모두 619/619, 436/436 일치).

### 3-8. 함께 발견한 것
Flink 출력(`agg.*`)의 Kafka 기록 시각이 **이벤트 시각(2019년)으로** 붙는다.
7일 보관 규칙에 바로 지워질 수 있다.


브로커가 **받은 시각**을 쓰게 했다.

### 3-9. `FLINK_PROPERTIES`에 `#` 주석을 쓰면 안 된다
```yaml
FLINK_PROPERTIES: |
  jobmanager.rpc.address: jobmanager
  # 이렇게 쓰면 Flink가 이 줄을 값의 일부로 읽어 시작에 실패한다
```
기본 compose 파일에도 들어 있었고, 그래서 고쳤다. 주석은 **블록 밖에** 쓴다.

## 4. 전체 흐름 첫 확인
```
재생기 → Kafka → Flink → ClickHouse,  제어기 → log.decisions → ClickHouse
```
가짜 데이터로 동작을 확인했다. 메모리는 Kafka·Flink·ClickHouse·제어기 합계 **약 2.5GB**.

문제가 하나 있었다. **제어기가 Kafka 준비 전에 접속하다 종료**됐다. 컨테이너가 시작된 것은
접속 가능한 것과 다르다.

```yaml
# docker-compose.yml
  kafka:
    healthcheck:                            # 컨테이너 시작 ≠ 접속 가능
      test: ["CMD-SHELL", "/opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list >/dev/null 2>&1"]
      interval: 5s
      retries: 30
  kafka-init:
    depends_on: { kafka: { condition: service_healthy } }
  controller:
    depends_on: { kafka-init: { condition: service_completed_successfully } }   # 토픽이 생긴 뒤 시작
```

## 5. 환경에서 걸린 것들
| 발견 | 대처 |
| --- | --- |
| PC에서 Kafka 접속 주소는 `localhost:29092` (9092는 컨테이너 내부용) | 재생기·제어기 기본값을 29092로 바꿈 |
| Git Bash에서 `docker exec`에 `/opt/...`를 주면 Windows 경로로 바뀜 | `MSYS_NO_PATHCONV=1` 또는 PowerShell |
| `core.autocrlf=true`라 새로 받으면 `.sh`가 CRLF가 되어 컨테이너에서 실패 | `.gitattributes`로 LF 고정 |
| Windows에 `make`가 없음 | PyCharm 실행 구성(`.idea/runConfigurations`) 사용 |
| 재생기 단일 프로세스 최대 전송 속도 | **약 39,000건/초** (3회 중앙값, 36,000~48,000) |

`.gitattributes`를 넣은 것은 작지만 중요하다. CRLF가 된 `.sh`는 컨테이너에서
`/bin/bash^M`을 찾다가 실패하고, 그 오류 메시지는 원인을 바로 알려 주지 않는다.

```
# .gitattributes
*.sh          text eol=lf
Dockerfile    text eol=lf
*.yml         text eol=lf
*.sql         text eol=lf
Makefile      text eol=lf
```

이 날은 발견만 하고 넘겼다. 다음 날(ADR-0008) 이 문제 하나로 하루를 썼고, 조합 33가지를
시뮬레이션으로 비교해 신호 방식을 통째로 바꿨다.

## 7. 이 날 배운 것
1. **"데이터는 다 읽었는데 집계에 없다"는 워터마크를 보라는 신호다.** 밀림이 0인데 결과가
   틀리면 읽기 문제가 아니라 시간 판정 문제다.
2. **PyFlink는 Python 함수를 조용히 무시할 수 있다.** 예외도 경고도 없다. 작업은 정상으로
   보이고 숫자만 틀린다. → 중요한 값은 REST API로 **직접 들여다봐야** 한다.
3. **한 문제를 고치려다 다른 원칙을 깨는 후보를 걸러내야 한다.** "Kafka 기록 시각을 2019년으로"는
   워터마크를 고치지만 7일 보관 규칙을 깬다.
4. **컨테이너가 시작된 것은 접속 가능한 것과 다르다.** healthcheck와 시작 순서가 필요하다.
