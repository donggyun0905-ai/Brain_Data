# 2026-10-19 — 학교 PC 구축, 병렬도 문제 해소, 수면 재생·오차 범위 구현, 전체 흐름 검증

> 그날 나온 ADR: 0012(학교 PC/Docker) · 0013(병렬도) · 0014(수면 재생 설계) ·
> 0015(오차 범위) · 0016(ClickHouse 적재) · 0017(처리 능력 되찾기)
> 단위 테스트 24개 → **53개**. 커밋 9개.

## 0. 이 날의 줄거리

학교 PC에서 처음 작업을 시작했다. 환경을 처음부터 깔고, 데이터를 다시 받아 변환했다.
Docker가 안 돌아 한동안 "브로커 없이 할 수 있는 일"만 하려 했는데, 알고 보니 WSL만 깔면 되는 문제였다.

그래서 이 날은 두 덩어리로 나뉜다.

1. **브로커 없이 한 일** — 병렬도 문제 정량화, 수면 재생 설계, 오차 범위 설계·구현
2. **Docker가 돌아간 뒤 한 일** — ClickHouse 적재 검증, 제어기 포함 전체 흐름, 모형 교정 실제 검증

2번에서 **1번에 만든 것들이 실제 데이터에서 깨지는 것**을 발견해 고쳤다. 이 날의 가장 큰 수확은
측정값이 아니라 "가짜 데이터에서 완벽한 코드가 실제 데이터에서 왜 깨지는가"였다.

## 1. 학교 PC 환경 구축

### 1-1. Python 3.12를 따로 깐 이유
PC에는 Python 3.14만 있었다. PyFlink 2.2.1은 **3.11/3.12용 설치 파일만** 있어서 3.13 이상에서는
`pip install apache-flink`가 아예 안 된다 (2026-10-16에 확인한 사실).

관리자 권한 없이 사용자 단위로 깔았다.

```bash
winget install --id Python.Python.3.12 --scope user \
  --accept-source-agreements --accept-package-agreements --disable-interactivity
```

기존 3.14는 그대로 두고 `py -3.12`로만 쓴다. `py -0p`로 둘 다 잡히는 것을 확인했다.

```bash
py -3.12 -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe -m pip install -e .      # ★ 이게 없으면 python -m databrain... 과 tools/ 가 안 돈다
.venv/Scripts/python.exe -m pytest -q             # 24 passed
```

**`pip install -e .`를 빼먹으면 안 된다.** `pyproject.toml`의 `[tool.setuptools.packages.find] where = ["src"]`
때문에 소스가 `src/` 아래 있는데, 이걸 안 하면 `src`가 `sys.path`에 안 들어가서
`python -m databrain.replayer.prepare`가 `ModuleNotFoundError`로 죽는다.
`pytest`는 `pyproject.toml`의 `pythonpath = ["src"]` 덕에 돌아가므로, **테스트는 통과하는데
실행은 안 되는** 혼란스러운 상태가 된다.

### 1-2. requirements.txt에 pandas가 빠져 있었다
`tools/compare_heavy.py`를 돌리려니 이렇게 죽었다.

```
_duckdb.InvalidInputException: Invalid Input Error: 'pandas' is required for this operation but it was not installed
```

`tools/compare_heavy.py`와 `tools/verify_shedding.py`가 pandas를 쓰는데 `requirements.txt`에 없었다.
집 PC에는 어쩌다 깔려 있어서 드러나지 않았던 것이다. **새 PC에서 깨끗하게 설치하면 도구가 전부 안 돈다.**

```diff
 confluent-kafka>=2.6
 duckdb>=1.1
+pandas>=2.2        # tools/compare_heavy.py, tools/verify_shedding.py (2026-10-19: 빠져 있어 새 PC에서 실행 실패)
 numpy>=2.0
```

> **교훈**: 의존성은 "내 PC에서 돌아간다"로 검증되지 않는다. 깨끗한 환경에서 한 번 깔아 봐야 드러난다.

### 1-3. 데이터 변환 (9GB CSV → 날짜별 Parquet)
Kaggle REES46 `2019-Nov.csv`(8.4GB)를 받아 변환했다.

```bash
.venv/Scripts/python.exe -m databrain.replayer.prepare data/raw/2019-Nov.csv data/parquet/2019-11
```

`prepare`는 **2단계**로 돈다 (ADR-0009). 1단계는 정렬 없이 날짜별로만 나누고(`_staging`), 2단계는
하루씩 시간순 정렬한다. 한 달을 한 번에 정렬하면 PC 메모리가 터지기 때문이다.

결과가 집 PC 실측과 **정확히 일치**했다.

```
67,501,979행 / 30일
11/01 1,445,360  …  11/14 3,069,726  11/15 6,220,416  11/16 6,502,957  11/17 6,395,377  …
```

11/15~17이 평소(약 170만)의 **3.7배** — ADR-0009가 10월 대신 11월을 고른 이유가 그대로 재현됐다.

압축이 `2019-Nov.csv`라는 **폴더** 안에 같은 이름 파일로 풀렸는데, DuckDB의 `read_csv_auto`가
폴더를 알아서 읽어 줘서 변환은 정상이었다. 행 수가 맞아 확인됐다.

**디스크**: C: 여유가 27GB → 11GB까지 떨어졌다. 변환이 끝나면 CSV는 역할이 끝나므로 지웠다.
지우기 전에 Parquet이 제대로 읽히는지 먼저 확인했다.

```
11/17 행수 6,395,377 | 시각 00:00:00 ~ 23:59:59 | event_id 종류 6,379,913
[('view', 5783241), ('cart', 426941), ('purchase', 185195)]
정렬 확인: 0 건 역순 (0이어야 정상)
```

> **순서가 중요하다**: 원본을 지우기 전에 변환 결과를 검증한다. 되돌릴 수 없는 일은 검증 뒤에 한다.

## 2. Docker가 안 돌았다 → WSL 설치 (ADR-0012)

### 2-1. 증상과 진단
`docker compose up`이 아무 컨테이너도 못 띄웠다. Docker 로그에 이것만 반복됐다.

```
[com.docker.backend.exe.otelmgr][W] still waiting to toggle VM Otel collector settings
in the VM after 27m31s: cannot toggle VM OTel collector, backend is not running
```

`backend is not running` — VM 자체가 안 뜬 것이다. Docker Desktop의 Linux 엔진은 WSL2나 Hyper-V가
필요하다. 확인해 보니 둘 다 없었다.

```bash
sc query LxssManager     # → "지정된 서비스가 설치된 서비스로는 없습니다" (WSL 기능 미설치)
sc query vmcompute       # → 같음 (Hyper-V 미설치)
wsl --list --verbose     # → 사용법만 출력 (배포판 0개)
```

### 2-2. 내가 틀린 진단을 했다
`net session`으로 권한을 확인하고 "계정이 일반 사용자"라고 단정했다. 그래서 ADR-0012에
"관리자 권한이 없어 설치 불가, 전산실에 요청 필요"로 적었다.

**틀렸다.** `net session`은 **"지금 이 셸이 관리자 권한으로 떠 있는가"**만 보는 검사다.
계정이 Administrators 그룹에 속하는지는 별개다.

```bash
net localgroup Administrators
# Members
# -------------------------------------------------------------------------------
# Administrator
# dita_810          ← 들어있다
```

UAC로 승인하면 설치할 수 있었다. ADR-0012에 정정을 달았다.

> **교훈**: "할 수 없다"는 결론은 "할 수 있다"보다 검증을 더 해야 한다. 잘못된 불가 판정은
> 멀쩡한 길을 막는다.

### 2-3. 해결
```powershell
# 관리자 PowerShell (UAC 승인)
wsl --install --no-distribution
# → 재시작
```

`--no-distribution`은 리눅스 배포판 없이 WSL 기능(+가상 머신 플랫폼)만 켜는 옵션이다.
Docker Desktop은 자기 배포판(`docker-desktop`)을 따로 쓰므로 Ubuntu 등이 필요 없다.

재시작 후:
```
기본 버전: 2 / WSL 버전: 3.0.1.0 / 커널 버전: 6.18.40.1-1
sc query LxssManager → 존재 (STOPPED = 필요할 때 시작되는 정상 상태)
```

Docker 엔진이 올라왔다. 메모리 할당 8.3GB — 집 PC와 같은 조건이라 `docker-compose.local.yml`의
가벼운 설정(ADR-0006)이 그대로 맞았다.

## 3. 거르기 병렬도 문제 해소 (ADR-0013)

### 3-1. 무엇이 걱정이었나
상위 사용자 판정은 `HeavyUserTracker`가 들고 있는 dict로 한다. 이 dict는 **Flink 작업
(서브태스크)마다 따로** 있다.

```python
# src/databrain/flink_jobs/main_job.py
class SheddingFilter(BroadcastProcessFunction):
    def open(self, runtime_context):
        self.heavy = HeavyUserTracker()   # ← 서브태스크마다 하나씩
```

그런데 토픽 칸 수가 다르다.

```bash
# infra/kafka/create_topics.sh
mk "${p}events.cart" 6
mk "${p}events.view" 12
```

같은 사용자의 조회와 장바구니가 **다른 서브태스크로 갈 수 있다**. 그러면 건수가 쪼개져 세어져
50건 기준에 못 미치고, 봇 안전장치가 풀릴 수 있다. 일지에는 "조회가 94%라 영향은 작을 것으로
**추측**"이라 적고 AWS 확인으로 미뤄 둔 상태였다.

### 3-2. 브로커 없이 미리 재는 방법
`tools/compare_parallel.py`를 만들었다. Kafka의 칸 배정과 Flink의 서브태스크 배정을 **코드로 재현**해
`HeavyUserTracker`를 병렬도별로 여러 개 돌린다.

```python
def java_hash(s: str) -> int:
    """Java String.hashCode (32비트 넘침 포함). Flink가 토픽 이름을 이 값으로 섞는다."""
    h = 0
    for ch in s:
        h = (31 * h + ord(ch)) & 0xFFFFFFFF
    return h - (1 << 32) if h >= (1 << 31) else h

def partition_of(user_id: str, n_parts: int, how: str) -> int:
    key = user_id.encode()
    return (murmur2(key) if how == "murmur2" else zlib.crc32(key)) % n_parts

def subtask_of(topic: str, partition: int, parallel: int) -> int:
    start = ((java_hash(topic) * 31) & 0x7FFFFFFF) % parallel
    return (start + partition) % parallel
```

**분배기를 두 종류 다 넣은 이유**: 재생기는 `confluent-kafka`(librdkafka)를 쓰고, librdkafka의
기본 분배기 `consistent_random`은 키가 있으면 **crc32**를 쓴다. Java 클라이언트 기본값은
**murmur2**다. 어느 쪽이 맞는지 확신할 수 없어 **둘 다 돌려 결과가 배정 방식에 민감한지** 보기로 했다.
(`CLAUDE.md`의 "추측한 값은 추측이라고 적는다" 규칙을 코드로 옮긴 것이다.)

평가 지표는 `tools/compare_heavy.py`의 `evaluate()`를 **그대로 재사용**했다. 그래야 ADR-0011 표와
숫자를 직접 비교할 수 있다. 새 지표를 만들면 "좋아졌는지 나빠졌는지"를 말할 수 없다.

### 3-3. 뜻밖의 발견: 쪼개짐이 100%였다
`경로 갈림 사용자% = 100.0`이 모든 병렬도에서 똑같이 나왔다. 병렬 4에서는 수학적으로 25%쯤이
같은 서브태스크에 와야 하는데 0%였다. 버그를 의심해 합성 사용자 10만 명으로 따로 확인했는데도 100%였다.

**버그가 아니라 산수였다.** 토픽 이름 해시에서 나온 시작값이 정확히 1 차이다.

```
병렬  2: view시작=0 cart시작=1
병렬  4: view시작=2 cart시작=3
병렬  6: view시작=2 cart시작=3
병렬 12: view시작=2 cart시작=3
```

병렬 4를 예로 들면, 12는 4의 배수라 `(crc%12)%4 = crc%4`이므로

```
서브태스크 차이 = (2 + crc) − (3 + crc%6) = 6·⌊crc/6⌋ − 1   (mod 4)
```

`6k − 1`은 **항상 홀수**여서 짝수 병렬도로 나눈 나머지가 0이 될 수 없다. 즉 **절대 같은
서브태스크에 못 온다.** 병렬 6·12도 같은 방식으로 0이 되지 않는다.

### 3-4. 그런데도 영향이 없었다
| 병렬도 | 쪼개진 사용자 | 판정 불일치% | 봇 판정% | 범주·분 p95 (통과 10%) |
| --- | --- | --- | --- | --- |
| 1 (정답) | 0% | — | 97.2 | 53.2 |
| 2 | **100%** | 0.02 | 97.2 | 53.2 |
| 4 | **100%** | 0.02 | 97.2 | 53.2 |
| 6 | **100%** | 0.02 | 97.2 | 53.2 |
| 12 | **100%** | 0.02 | 97.2 | 53.2 |

crc32와 murmur2 결과가 모든 칸에서 같았다.

**왜 영향이 없는가**: 상위 판정이 걸리는 사용자는 사실상 봇뿐이고(ADR-0011), 봇의 활동은 거의
전부 조회다. 조회는 한 사용자가 한 칸에만 들어가므로 조회 쪽 dict가 그 사용자의 93~100%를 그대로 본다.
쪼개짐이 해를 끼치려면 '조회와 장바구니를 비슷한 양으로 만드는 무거운 사용자'가 있어야 하는데,
11월 데이터에서 장바구니는 전체의 4.49%뿐이라 그런 사용자가 없다.

**이 결론이 가정에 기대지 않는 이유**: 칸 배정과 서브태스크 배정은 코드를 읽고 세운 가정이다.
그러나 어떤 규칙이든 쪼개짐은 0%와 100% 사이에 있고, 이 측정은 **양 끝을 다 재었다**
(병렬 1 = 0%, 병렬 2~12 = 100%). 가정이 틀려도 결과는 두 값 사이에 있으므로 결론은 바뀌지 않는다.

### 3-5. 결정
토픽 칸 수를 맞추거나 상위 판정을 조회만으로 세는 **변경은 하지 않는다.** 이득이 없다.
일지의 "AWS에서 다시 돌리기" 항목은 우선순위를 낮췄다 (없애지는 않았다 — 이번 측정은
'상위 판정'만 모형으로 본 것이고 Flink의 실제 창 집계·워터마크는 포함하지 않았다).

ADR-0010에 "Kafka 키가 user_id라서 한 사용자는 늘 같은 필터 작업으로 간다"고 적혀 있었는데,
조회끼리는 맞지만 조회와 장바구니는 갈라진다. 교차 참조를 달았다.

## 4. 수면 재생 설계와 모형 교정 (ADR-0014)

### 4-1. ADR 번호가 비어 있었다
ADR-0002의 마지막 줄이 이랬다.

> 버린 양은 알고리즘과 무관하게 처리 능력이 정한다 → 수면 재생은 문턱값이 아니라
> 처리 능력 모델을 고친다 **(ADR-0006 예정)**

그런데 0006번은 '개발 PC와 AWS'에 쓰였고, **수면 재생 기록은 비어 있었다.** 프로젝트의 가장 큰
차별점인데 설계 문서가 없는 상태였다. ADR-0014로 채우고, ADR-0002의 잘못된 앞방향 참조도 고쳤다.

### 4-2. 핵심 통찰
밤에 고칠 것은 '얼마나 거를지'가 아니라 **'내 처리 능력이 얼마인지'**다. 제어기의 계산은
`CapacityModel`의 숫자에서 나오므로, 그 숫자가 실제와 가까워지면 **같은 알고리즘이 저절로 덜 버린다.**

```python
# src/databrain/controller/rate_model.py
@dataclass(frozen=True)
class CapacityModel:
    capacity_eps: float            # 무거운 처리가 1초에 할 수 있는 작업량 ← 밤에 고칠 값
    filter_cost: float = 0.05      # 거르는 판단 하나의 비용 ← 밤에 고칠 값
    margin: float = 0.9            # 조절 취향
    target_lag_s: float = 2.0      # 조절 취향
    ...
```

위 두 개는 **물리량**(측정으로 알아낼 수 있다), 아래는 **취향**(탐색으로 고른다). 이 구분이 설계를 갈랐다.

### 4-3. 세 단계
| 단계 | 하는 일 | 상태 |
| --- | --- | --- |
| 1. 재계산 | 보관본을 `replay.` 토픽에 원래 간격대로 보내 전량 집계 → ClickHouse `status`를 `estimate` → `confirmed` | 설계만 (12월) |
| 2. 모형 교정 | 그날 `log.decisions`만으로 `capacity_eps`·`filter_cost`를 되찾는다 | **구현·검증 완료** |
| 3. 조절값 탐색 | 2단계로 맞춘 모형 + 그날 유입 곡선을 시뮬레이터에 넣고 optuna로 취향 값 탐색 | 설계만 (2월) |

**3단계를 실제 스택으로 하지 않는 이유**: 하루 재생이 100배속에서도 약 15분이다. 후보 100개면
25시간이라 밤에 끝나지 않는다. 그래서 탐색은 시뮬레이터에서 한다.

**순환 논리를 막는 장치**: 시뮬레이터로 탐색하면 '내 모형에 맞춰 내 모형을 고치는' 꼴이 된다.
그래서 탐색 **전에** 관문을 둔다 — 교정한 모형을 넣은 시뮬레이터가 **그날 실제로 일어난 일**
(신선도 p99, 버린 비율)을 오차 안에서 재현하지 못하면 그 밤의 교정을 건너뛴다. 정답이 모형이
아니라 측정에서 온다.

### 4-4. 2단계를 어떻게 구현했나
비용 모형은 시뮬레이터와 같다 (`sim/compare_controllers.py`의 `cost`).

```
작업량 = filter_cost × 읽은 수 + 남긴 수
```

읽은 수는 뺄셈으로 나온다. 밀림은 '들어온 것 − 읽은 것'이 쌓인 양이므로

```
읽은 수(구간) = 그 구간에 들어온 수 − (구간 끝 밀림 − 구간 시작 밀림)
```

밀림이 쌓여 있는 동안에는 처리 단계가 늘 꽉 차 있으므로 작업량 = capacity다. 즉

```
남긴 수 = capacity − filter_cost × 읽은 수
```

꽉 찬 구간의 점들을 (읽은 수, 남긴 수) 평면에 놓으면 **기울기 −filter_cost, 세로 절편 capacity인
직선** 위에 모인다. 통과 비율이 낮을 때는 같은 작업량으로 더 많이 읽으므로 점들이 오른쪽 아래로
퍼지고, **그 퍼짐이 직선을 정할 수 있게 해 주는 정보**다.

**왜 그냥 최소제곱을 쓰지 않는가**: 작업량은 capacity를 넘을 수 없으므로 모든 점이 직선의
**아래쪽**에 있다. 꽉 차지 않은 순간이 섞이면 직선이 아래로 끌려 내려가 capacity를 낮게 본다.
그래서 읽은 수로 구간을 나눠 각 구간의 위쪽 분위수만 모아 직선을 맞춘다 (위쪽 외피).

### 4-5. 테스트가 버그 2개를 잡았다

**버그 1 — 꽉 찬 구간 판정.** 처음엔 이렇게 썼다.

```python
# 틀린 코드
sat = [s for s in st if s.read > 0 and s.backlog_start >= min_backlog_s * (s.arrivals / s.dt_s)]
```

한가한 가짜 하루(유입 500/초, 처리 능력 10,000)에서 **199구간 전부가 '꽉 찼다'로 판정**됐다.
기록된 밀림에는 그 구간의 유입이 이미 들어 있어서, 큐를 다 비운 한가한 순간도 `밀림 = 유입`이
되어 꽉 찬 것처럼 보였던 것이다.

```python
# 고친 코드 — '이미 쌓여 있던 것 중 못 읽고 남은 양'으로 판정
sat = [s for s in st
       if s.read > 0 and (s.backlog_start - s.read) >= min_backlog_s * (s.read / s.dt_s)]
```

**버그 2 — 외피를 집는 방식.** 처음엔 구간마다 `x`는 평균, `y`는 분위수로 따로 집었다.

```python
# 틀린 코드
pts.append((sum(xs) / len(xs), _quantile(ys, q)))
```

`filter_cost`가 체계적으로 9% 낮게 나왔다 (정답 0.05 → 0.0456, 0.20 → 0.179). 남긴 수는 읽은 수가
적을 때 크므로, 분위수로 집힌 `y`는 평균보다 **작은 `x`의 것**이다. 짝이 깨져 기울기가 완만해진 것이다.

```python
# 고친 코드 — 짝을 깨지 않고 구간 하나를 통째로 집는다
by_kept = sorted(chunk, key=lambda s: s.kept / s.dt_s)
pick = by_kept[min(len(by_kept) - 1, int(q * (len(by_kept) - 1) + 0.5))]
pts.append((pick.read / pick.dt_s, pick.kept / pick.dt_s))
```

## 5. 오차 범위 구현 (ADR-0015)

### 5-1. H2가 요구하는 것
기획서를 읽어 H2의 정확한 문장을 확인했다 (저장소에는 없어서 Claude Docs로 기획서를 읽었다).

> **H2 정직한 정확도**: 덜 본 데이터의 추정치와 오차 범위를 믿을 수 있다
> ① 화면에 표시한 95% 오차 범위가 실제값을 95% 안팎으로 포함
> ② 퍼널 전환율 편향 1%p 이내
> ③ 통과 비율 10% 이상에서 **5분 단위** 조회수 오차 3% 이내
> 시뮬레이션 예측: 혼합 샘플링 퍼널 편향 0.5%p 이내. **③은 실측 필요**

①을 계산하는 코드가 **아예 없었고**, ③은 **아직 안 재어 본 상태**였다.

### 5-2. 단순 이항 분산을 쓰면 안 되는 이유
혼합 샘플링은 두 방식이 섞여 있다.
- 상위 사용자: 이벤트마다 따로 뽑는다 → 서로 **독립**
- 나머지 사용자: 사용자 해시로 통째로 뽑는다 → 한 사람의 이벤트는 **다 들어오거나 다 빠진다**

한 사람이 그 칸에 10건을 만들었다면 그 10건은 같이 움직인다. 흔들림은 '1건 10개'가 아니라
'10건 1개'짜리다. 단순 이항 분산을 쓰면 구간이 좁아진다.

실측했다: **통과 10%에서 적중률 80% 미만** (`tests/test_interval.py`의
`test_naive_binomial_interval_is_too_narrow`). 이 테스트는 "이 모듈이 왜 필요한가"를 코드로 남긴 것이다.

### 5-3. 묶음 추출로 보면 더해지는 식이 된다
'묶음(cluster)'을 이렇게 정하면 두 방식을 한 식으로 쓸 수 있다.
- 상위 사용자의 이벤트 하나 = 묶음 하나 (크기 1)
- 나머지 사용자의 (사용자, 통과 비율)별 이벤트 뭉치 = 묶음 하나 (크기 A)

```
추정치 Y = Σ_c (A_c / r_c) × [뽑혔는가]
분산   V = Σ_c A_c² (1 − r_c) / r_c
남긴 것만으로 재는 값 V^ = Σ_{남은 c} A_c² (1 − r_c) / r_c²
```

`V^`의 기대값이 정확히 `V`가 된다 (뽑힐 확률이 `r_c`이므로 한 번 더 나눈다).

**집계 코드를 거의 안 바꿔도 되는 이유**: `A²`는 하나씩 더해 만들 수 있다. 묶음의 `i`번째
이벤트에서 `2i − 1`을 더하면 합이 `A²`이다 (1+3+5+…+(2A−1) = A²). 따라서 남긴 이벤트마다

```python
# src/databrain/sampling/interval.py
def variance_part(rate: float, cluster_index: int) -> float:
    return (2 * cluster_index - 1) * (1.0 - rate) / (rate * rate)
```

를 실어 보내고 칸마다 **그냥 더하면** 그 칸의 `V^`가 된다. `est_count`를 더하는 것과 똑같은
모양이라 집계 단계에 숫자 하나만 늘리면 된다.

### 5-4. Flink에 넣기 전에 찾은 버그
`ClusterIndex`를 처음엔 "분이 바뀌면 상태를 다 비우기"로 썼다.

```python
# 틀린 코드
if minute_ms != self._minute:
    self._n.clear()
    self._minute = minute_ms
```

`main_job.py`는 조회·장바구니 토픽을 `union`해서 처리한다. **두 흐름에서 분이 뒤섞여 들어오므로
상태가 계속 날아간다.** 창을 열쇠에 넣고 오래된 분만 치우도록 바꿨다.

```python
# 고친 코드
if self._max_minute is None or minute_ms > self._max_minute:
    self._max_minute = minute_ms
    self._prune()
key = (minute_ms, user_id, cell, round(rate, self.rate_digits))
```

### 5-5. 적중률 실측 (오프라인, 11/17 14시 조회 433,606건)
| 창 | 통과 비율 | 적중률% (기준 ①) | 창 총량 오차 p95% (기준 ③) |
| --- | --- | --- | --- |
| 1분 | 50% | 94.7 (94.3~94.8) | 3.3 (3.1~3.7) |
| 1분 | 10% | 91.9 (91.9~92.5) | 9.7 (9.5~9.8) |
| 5분 | 50% | 93.1 (93.1~93.3) | 2.3 (2.2~2.7) |
| **5분** | **10%** | **86.0 (86.0~86.4)** | **7.2 (6.6~7.4)** |

**기준 ③은 달성 불가다.** 목표 3%인데 실측 7.2%로 2.4배다. 3%는 통과 비율 약 50%에서나 지켜진다.

**기준 ①은 식이 맞고 추정이 원인이다.** 정답 분산(모든 묶음을 다 안다고 가정)으로 구간을 만들면
적중률이 어디서나 목표에 있다.

| 창 | 통과 | 추정 분산 | **정답 분산** | 차이 |
| --- | --- | --- | --- | --- |
| 1분 | 10% | 92.5% | 94.3% | 1.8%p |
| 5분 | 10% | **86.0%** | **95.5%** | **9.5%p** |

`V^`는 기대값은 맞지만 **분포가 오른쪽으로 치우쳐** 있어 절반 넘는 경우에 정답보다 작게 나온다.
묶음 크기가 들쭉날쭉할 때(한 사람이 5분 동안 수십 건) 큰 묶음은 대개 안 뽑히므로 `V^`가 그 몫을
놓친다. 창이 커질수록 묶음 크기 편차가 커져서 더 심해진다.

### 5-6. 결정
1. 분산 식(묶음 추출)을 채택
2. **화면 기본 단위는 1분.** 1분에서는 추정만으로도 적중률 91.9~94.7%다
3. **5분 이상은 수면 재생 확정값에서 `Σ A²`를 가져와 계산한다** (ADR-0014 1단계와 연결).
   밤의 재계산은 전량을 처리하므로 묶음 크기 제곱합을 **정확히** 낼 수 있다
   → 수면 재생이 정확도에도 쓰이는 두 번째 길이다
4. **기준 ③은 기획서 갱신을 요청한다.** (가) `통과 10% 이상에서 5분 8% 이내`를 권한다.
   H2의 이름이 '정직한 정확도'이므로, 못 지킬 숫자를 목표로 두는 것보다 지킬 수 있는 숫자를 적고
   오차 범위를 함께 띄우는 쪽이 가설의 뜻에 맞다

### 6-4. 이 날 가장 비싼 교훈 — 검증 도구가 조용히 거짓말한다
같은 종류의 실수를 **세 번** 했다.

**(1) `verify_flink.replay()`가 stderr를 버린다.**
```python
r = subprocess.run([...], capture_output=True, text=True, env=ENV, timeout=600)
print("재생:", r.stdout.strip()[-60:])    # ← 종료 코드도 stderr도 안 본다
```
경로가 틀려 한 건도 안 보냈는데 조용히 다음으로 넘어가 4분을 기다렸다. 내 도구에서는 터뜨린다.
```python

    raise RuntimeError(f"재생 실패 (코드 {r.returncode}): {(r.stderr or r.stdout).strip()[-500:]}")
```
재생 뒤 이벤트 토픽 건수가 0이 아닌지도 확인한다.

**(2) ClickHouse 행 수만 세며 기다렸다.** 구매 쪽(1,388건)이 먼저 끝나 25초간 조용해지자,
메인 쪽(45,176건, 2단계 집계)이 아직 계산 중인데도 빠져나와 **'agg_minute 0행'으로 오판**했다.

**(3) Flink 출력 건수만 봐도 같은 일이 난다.** 메인의 2단계 집계는 한참 읽다가 창이 닫힐 때
몰아서 내보내므로, 읽는 동안 출력이 조용하다.

최종 해결 — **출력 건수와 읽은 건수가 둘 다 멈춘 뒤에야** 다음으로 간다.
```python
def wait_pipeline(quiet_s=40.0, limit_s=900.0):
    while True:
        cur, now = {**agg_offsets(), "_read": jobs_read()}, time.time()
        if cur != prev:
            prev, last_change = cur, now
        if last_change and sum(agg_offsets().values()) > 0 and now - last_change >= quiet_s:
            break
```

판정도 갈라 적는다. 예전 코드는 `1회차 == 2회차`만 보고 1회차가 이미 틀렸는데도 '실패'라고
보고했다. 이제 **1회차가 온전히 맞았나 → 중복이 실제로 들어왔나 → 그래도 `FINAL`이 같은가**
순서로 보고, 조건이 안 되면 **'판정 불가'**로 쓴다. **틀린 판정보다 판정 불가가 낫다.**

**사람이 지킬 규칙도 하나 생겼다.** 검증이 돌고 있는 동안에는 스택을 **조회만** 한다.
이 날 돌고 있는 검증이 띄운 Flink 작업을 '수동 제출한 것'으로 착각해 취소해 검증을 깨뜨렸다.

### 6-5. 함께 알게 된 것
`init.sql`은 `CREATE TABLE IF NOT EXISTS`이고 ClickHouse 이미지는 **익명 볼륨**을 쓴다.
열을 늘려도 기존 DB에는 반영되지 않고, `--force-recreate`로도 안 된다.
```bash
docker compose ... rm -sfv clickhouse    # 볼륨까지 지워야 init.sql이 다시 돈다
docker compose ... up -d clickhouse
```
데이터가 쌓인 뒤에는 `ALTER TABLE ... ADD COLUMN`을 써야 한다.

## 7. 오차 범위 열을 파이프라인에 넣기

### 7-1. `main_job.py` 수정
거르기 단계가 `heavy` 여부도 내보내게 했다. 오차 범위는 상위 사용자(이벤트 단위)와
나머지(사용자 단위)의 흔들림이 다르므로 뒤 단계에서 그 구분이 필요하다.

```python
# 전
if keep(h.user_id, h.event_id, rate, self.heavy.is_heavy(h.user_id)):
    yield lane, raw, rate

# 후
hv = self.heavy.is_heavy(h.user_id)
if keep(h.user_id, h.event_id, rate, hv):
    yield lane, raw, rate, hv
```

`to_record`는 묶음 안 순번을 세야 하므로 **상태를 가진 `MapFunction`**으로 바꿨다.
`open()`에서 `ClusterIndex`를 만든다. (거르기 단계에서는 못 한다 — 그 단계는 머리말만 읽고
본문을 파싱하지 않아서 **칸(범주)을 모른다**.)

```python
class ToRecord(MapFunction):
    def open(self, runtime_context):
        self.ci = ClusterIndex()

    def map(self, value):
        lane, raw, rate, heavy = value
        h, body = wire.decode(raw)
        ts = h.event_ms
        cat = body.get("category_code", "etc")
        idx = self.ci.next(h.user_id, f"{body['event_type']}|{cat}", ts - ts % 60_000, rate, heavy)
        return (key, ts, weight(rate), variance_part(rate, idx), 1,
                int(time.time() * 1000) - h.ingest_ms)
```

**흔들림 합을 어디에 넣었나**: 메인 경로에서 쓰이지 않던 슬롯(`가중 매출`, 항상 `0.0`)을 썼다.

```python
def merge(a, b):
    """가중 개수와 흔들림 합은 둘 다 그냥 더해진다 (2단계 집계에서도 같은 함수를 쓴다)."""
    return a[0], max(a[1], b[1]), a[2] + b[2], a[3] + b[3], a[4] + b[4], max(a[5], b[5])
```

`merge`가 **이미 그 자리를 더하고 있어서** 2단계 집계 구조를 하나도 바꾸지 않았다.
튜플 길이도 그대로다. 새 칸을 만들었다면 `merge`와 소금 제거 `map`을 둘 다 고쳐야 했다.

### 7-2. ClickHouse 쪽
`agg_minute_q`(Kafka 엔진) / `agg_minute`(저장) / `agg_minute_mv`(구체화 뷰) 세 군데에
`var_sum Float64`를 넣고, 화면이 바로 쓸 뷰를 만들었다.

```sql
CREATE VIEW IF NOT EXISTS databrain.agg_minute_shown AS
SELECT event_type, category_code, minute, status,
       est_count,
       1.959963984540054 * sqrt(var_sum) AS half_width,
       greatest(0, est_count - 1.959963984540054 * sqrt(var_sum)) AS lo,
       est_count + 1.959963984540054 * sqrt(var_sum) AS hi,
       if(est_count > 0, 1.959963984540054 * sqrt(var_sum) / est_count, 0) AS rel_half_width,
       raw_count, max_fresh_ms
FROM databrain.agg_minute FINAL;
```

전부 통과한 칸은 `var_sum = 0` → 반폭 0 → **확정값으로 읽힌다.**
5분 이상으로 묶어 볼 때는 흔들림 합을 그냥 더하면 과소평가되므로(§5-5) 이 뷰는 1분 단위만 제공한다.

```

평균 상대 반폭 46.1%  (오프라인 모형 49.0%)  ← 구현이 모형과 같은 값을 낸다
```

### 8-4. 새 추정기: 여러 초를 묶고, 남긴 수를 쓰지 않는다
두 가지를 바꿨다 (`fit_from_rates`).

**(1) 창으로 묶으면 중간 요동이 상쇄된다.**
```
읽은 총수 = 창 동안 유입 총합 − (창 끝 밀림 − 창 시작 밀림)
```
중간 초의 밀림 값이 식에서 사라진다. **깎기 전에 묶는 것이 핵심이다.**

**(2) 남긴 수를 아예 쓰지 않는다.** 꽉 찬 동안에는
```
읽은 수(초) = capacity / (filter_cost + 그 초의 실효 비율)
```
이고, **실효 비율은 기록에 그대로 있다.**

```python
def effective_rate(d: Decision) -> float:
    """큐에 쌓인 경로 비중으로 가중한 통과 비율. 시뮬레이터의 비용 식과 같다."""
    q = max(0.0, d.backlog_cart) + max(0.0, d.backlog_view)
    if q <= 0:
        return (d.cart + d.view) / 2.0
    return (max(0.0, d.backlog_cart) * d.cart + max(0.0, d.backlog_view) * d.view) / q
```

그러면 창마다 `R = capacity × Σ 1/(filter_cost + 실효 비율)`이 되어 최소제곱으로 맞출 수 있다.
`filter_cost`를 격자로 훑고, 그 값마다 `capacity`는 닫힌 식으로 바로 나온다.

```python
for fc in fc_grid:
    sw = [w.s_of(fc) for w in wins]
    cap = sum(w.read * s for w, s in zip(wins, sw)) / sum(s * s for s in sw)
    sse = sum((w.read - cap * s) ** 2 for w, s in zip(wins, sw))
    if best is None or sse < best[0]:
        best = (sse, cap, fc)
```

### 8-8. 이 숫자가 뜻하는 것
- **제어기에 처리 능력을 약 1.75배 과대평가해 주고 있었다** (1,200 vs 실측 687).
  ADR-0002는 50% 과대평가에도 신선도 0.9초(목표 5초)였다고 했지만 여기선 75%다.
  **수면 재생이 밤마다 고칠 대상이 바로 이 값이고, 그게 실제로 가능하다는 것이 처음 확인됐다.**
- **`filter_cost` 첫 측정치는 약 0.165다.** ADR-0005가 'E1에서 측정'으로 미뤄 둔 값이고,
  기획서 가정 0.05의 **3.3배**다. 머리말만 읽고 거르는 비용이 생각보다 비싸다.

**이 숫자를 확정값으로 쓰지 않는다.** 학교 PC는 다른 작업과 자원을 나눠 쓴다. `week1.md`에도
PC 처리량이 같은 조건에서 1,151~3,280건/초로 흔들린다고 적혀 있다. `filter_cost`가
0.120~0.175로 벌어지는 것도 그 영향으로 추측한다. 이 측정은 **'방법이 작동한다'는 증거**로 쓰고,
확정값은 실험 장비(EC2)에서 잰다 (ADR-0006).

### 8-9. 1초 방식을 지우지 않은 이유
비교 대상으로 남겼다. 처리 위치 신호가 더 촘촘해지면(예: 처리 건수를 직접 기록) 다시 쓸 수 있고,
**두 방식이 어긋나는 것 자체가 신호 품질을 알려 준다.**

## 9. 이 날 배운 것

1. **가짜 데이터에서 완벽한 코드가 실제 데이터에서 깨지는 방식은 '잡음'이 아니라 '구조'다.**
   `synth`는 매초 정확히 `capacity/cost`만큼 처리한다. 실제 Flink는 묶음으로 뛴다.
   잡음 내성 테스트(±100~±10,000건)를 통과했어도 그 구조 차이는 못 잡았다.
2. **거부해야 할 상황에서 그럴듯한 값을 내놓는 것이 가장 위험한 실패다.** 명백히 틀린 값은 눈에
   띄지만, 한가한 하루에서 '유입 속도'를 '처리 능력'이라고 내놓으면 아무도 모른다.
   같은 함정에 두 추정기 모두 빠졌고, 둘 다 테스트가 잡았다.
3. **검증 도구가 조용히 잘못된 결론을 내면 그 날의 모든 측정이 쓸모없다.** 이 날 세 번 당했고
   한 번은 '거짓 실패'까지 만들었다. **틀린 판정보다 판정 불가가 낫다.**
4. **의존성과 환경은 "내 PC에서 돌아간다"로 검증되지 않는다.** pandas 누락, 컨테이너 이름 고정,
   `pip install -e .` 누락 — 모두 깨끗한 새 PC에서만 드러났다.
5. **"할 수 없다"는 결론은 "할 수 있다"보다 검증을 더 해야 한다.** `net session` 하나로
   "관리자 권한 없음"을 단정해 Docker를 포기할 뻔했다.
6. **원본을 지우기 전에 변환 결과를 검증한다.** 되돌릴 수 없는 일은 검증 뒤에.
7. **실험 중에는 시스템을 조회만 한다.** 돌고 있는 검증의 Flink 작업을 취소해 검증을 깨뜨렸다.
