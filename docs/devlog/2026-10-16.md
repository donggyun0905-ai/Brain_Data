> 그날 나온 ADR: 0001(기본 구성) · 0002(예측형 제어기) · 0003(혼합 샘플링) ·

> 단위 테스트 17개. 이 날은 **코드를 거의 안 쓰고 숫자로 결정을 내린 날**이다.

## 0. 이 날 한 일
브로커도 Flink도 띄우지 않고, **시뮬레이션과 패키지 열어 보기만으로** 설계 원칙을 확정했다.
이유는 분명하다 — 이 프로젝트의 핵심 주장("덜 보고도 화면을 맞게 유지한다")이 성립하지 않으면
나머지를 만들 이유가 없다. 먼저 종이에서 깨뜨려 보고, 살아남은 것만 구현하기로 했다.

## 1. 기본 구성 선택 (ADR-0001)

| 역할 | 선택 | 비교 대상 | 고른 이유 |
| --- | --- | --- | --- |
| 이벤트 통로 | **Kafka** | Redpanda | 종류별 토픽, 보관, 시각 기준 재읽기. 업계 표준 |
| 실시간 처리 | **PyFlink 2.2** | Spark Structured Streaming | 브로드캐스트 상태로 **재시작 없이 비율 변경**, 이벤트 시간 처리 |
| 실시간 저장 | **ClickHouse** | PostgreSQL | 대량 입력과 초 단위 집계 조회, Kafka 엔진 |
| 장기 저장 | **Iceberg + MinIO** | 일반 Parquet | 원본 전체 보관, 과거 시점 조회 |

**포기한 것을 적어 둔 것이 중요하다.**
- Java Flink의 성능과 커넥터 대신 Python의 학습 속도를 택했다 → 그래서 **처리량 실험은
  '절대값'이 아니라 '상대 비교'로 해석한다**
- 관리형 서비스(MSK, EMR)를 쓰지 않아 직접 운영 부담이 있다 → 대신 비용과 학습 효과

> PyFlink를 고른 결정이 뒤에 비싼 값을 치른다. 2026-10-17에 `from_source`가 Python
> `TimestampAssigner`를 조용히 무시하는 문제(ADR-0007)를, 10-19에는 처리 위치 신호가
> 묶음으로 뛰는 문제(ADR-0017)를 만난다.

## 2. 제어 알고리즘 비교 (ADR-0002)

### 2-1. 무엇을 비교했나
`sim/compare_controllers.py`로 세 알고리즘을 같은 장면(조회 10배 폭증)에 넣었다.

| 알고리즘 | 작동 방식 | 신선도 p99 | 조회 버린 비율 | 조절 횟수 |
| --- | --- | --- | --- | --- |
| 단계형 | 밀림이 목표를 넘으면 미리 정한 비율 단계를 한 칸 내린다 | 1.9초 | 58% | 16 |
| AIMD | TCP 혼잡 제어처럼 곱셈으로 줄이고 덧셈으로 늘린다 | 1.9초 | 57% | 36 |
| **예측형 + 되먹임** | 지금 유입과 밀린 양으로 **필요한 비율을 직접 계산**한다 | **0.1초** | 58% | 24 |
| (조절 없음) | 아무것도 안 한다 | 810초 | — | — |

### 2-2. 예측형이 하는 계산
```python
# sim/compare_controllers.py 의 "ff" 분기 (실제 코드는 controller/rate_model.py)
R = rc_in + rv_in + q / TARGET_LAG          # 밀린 것을 목표 시간 안에 비우려면 필요한 읽기 속도
sc = (rc_in + qc / TARGET_LAG) / R          # 그중 장바구니 몫
sv = 1 - sc
per = 0.9 * CAP * cap_est / R - FC          # 읽은 이벤트 하나당 쓸 수 있는 처리량 (여유 10%)
want_v = (per - sc * 1.0) / max(sv, 1e-9)   # 장바구니는 1.0으로 두고 조회를 맞춘다
```

단계형·AIMD는 "밀림을 보고 한 칸 움직인다"(반응형)인데, 예측형은 **"지금 상태에서 필요한 값을
바로 계산한다"**. 그래서 한 번에 제자리를 찾고 신선도가 19배 좋아진다.

### 2-3. 처리 능력을 잘못 알아도 괜찮은가
처리 능력 추정을 일부러 틀리게 주고 돌렸다.

| 처리 능력 추정 | 신선도 p99 |
| --- | --- |
| 20% 낮게 | 0.1초 |
| 20% 높게 | 0.4초 |
| 50% 높게 | 0.9초 |

목표 5초 안에 다 들어온다. **이 표가 뒤에 두 번 인용된다** — ADR-0014(수면 재생)에서
"잡음으로 capacity가 +12.7% 편향돼도 견딘다"의 근거로, 2026-10-19에 "실제로는 75% 과대평가였다"를
판단하는 기준으로.

### 2-4. 이 날 가장 중요한 발견
> **버린 양은 알고리즘과 무관하게 처리 능력이 정한다** (셋 다 약 58%).

세 알고리즘의 버린 비율이 57~58%로 같다. 알고리즘은 **신선도**를 바꿀 뿐 **버린 양**은 못 바꾼다.
버린 양을 줄이려면 처리 능력을 더 정확히 알아야 한다.

→ 그래서 **수면 재생은 문턱값이 아니라 처리 능력 모델을 고치는 일**로 방향이 정해졌다.
(이 결정문은 번호가 비어 있다가 2026-10-19에 ADR-0014로 채워졌다.)

### 2-5. 밀림은 Kafka에서 직접 읽는다
Prometheus 기본 수집 주기는 15초인데 제어기는 1초마다 판단한다. 15초 묵은 값으로 1초 판단을 하면
안 되므로, 제어기는 Kafka 관리 API로 직접 읽는다. Prometheus는 **화면용**으로만 쓴다.

> 이 결정도 2026-10-18에 한 번 더 뒤집힌다 — Kafka 커밋 위치조차 7~9초 묵어 있었다 (ADR-0008).

## 3. 샘플링 방식 비교 (ADR-0003)

### 3-1. 왜 '무작위로 10%만 보기'가 안 되는가
`sim/compare_sampling.py`로 1분 조회 6만 건, 긴 꼬리 사용자 분포(파레토)에서 세 방식을 비교했다.

| 통과 비율 | 이벤트 무작위 (총량 오차 / 퍼널 왜곡) | 사용자 해시 | 혼합 |
| --- | --- | --- | --- |
| 50% | 0.8% / **+2.8%p** | **4.9%** / +0.0%p | 1.5% / +0.0%p |
| 10% | 2.3% / **+9.8%p** | **7.6%** / +0.3%p | 5.6% / +0.0%p |
| 2% | 5.5% / **+15.8%p** | **18.2%** / +1.1%p | 5.4% / −0.5%p |

- **이벤트 무작위**: 총량은 정확한데 **퍼널(세션 전환율)을 최대 16%p 왜곡**한다.
  한 세션의 조회 10건 중 2건만 남으면 그 세션은 '조회 2건 세션'으로 보이고, 조회가 다 사라진
  장바구니 세션은 분모에서 빠진다
- **사용자 해시**: 세션은 통째로 보존되는데 **총량 오차가 최대 18%**다. 많이 보는 소수가
  통째로 들어가거나 빠지면 총량이 크게 흔들린다
- **혼합**: 활동량 상위 사용자는 이벤트 단위, 나머지는 사용자 해시 → 둘 다 해결

### 3-2. 겹치는 임계값
`hash(user) < rate`로 판단한다. 그러면 5%에 뽑힌 사용자는 10%에도 **항상** 포함된다.
비율이 바뀌어도 이미 보던 사용자의 세션이 끊기지 않는다.

```python
# src/databrain/sampling/hashing.py
def keep(user_id, event_id, rate, heavy):
    if heavy:
        return unit_hash(f"e:{user_id}:{event_id}") < rate   # 이벤트마다 따로
    return unit_hash(f"u:{user_id}") < rate                  # 사람 단위, 겹치는 임계값
```

### 3-3. 이 비교가 가설을 바꿨다
> 1분 단위 2% 오차 목표는 낮은 비율에서 **불가능** → H2를 '표시한 오차 범위의 적중률'로 변경

처음 기획의 '보정 오차 0.6%'는 모든 사용자가 비슷하게 행동한다는 가정에서 나온 낙관적인 값이었다.
실제와 비슷한 긴 꼬리 분포에서는 그 숫자가 안 나온다.

그래서 목표를 **"오차를 없앤다"에서 "오차 범위를 정직하게 표시한다"로 바꿨다.**
이것이 프로젝트의 성격을 정한 결정이다. (그 오차 범위를 실제로 계산하는 코드는
2026-10-19에 ADR-0015로 만들었고, 그때 기준 ③이 달성 불가라는 것도 드러났다.)

## 4. 파티션 키 (ADR-0004)

| 기준 | 장점 | 단점 |
| --- | --- | --- |
| **user_id (채택)** | 세션 순서 유지, 고른 분산, 사용자 해시 샘플링과 일치 | 상품별 집계는 다시 모아야 함 |
| product_id | 상품 집계가 쉬움 | 타임딜 상품 하나로 특정 파티션 과부하 |
| 무작위 | 가장 고른 분산 | 세션 순서 깨짐 |

상품·카테고리 집계는 `(키, 소금 0~7)`로 부분 합계를 낸 뒤 소금을 떼고 최종 합계를 내는
**2단계 집계**로 해결했다.

```python
# src/databrain/flink_jobs/main_job.py
salt = int(unit_hash(f"s:{h.user_id}") * SALT_BUCKETS)
key = f"{body['event_type']}|{cat}|{salt}"                 # 1단계: 소금 포함
...
partial = kept.key_by(lambda r: r[0]).window(...).reduce(merge)
final = (partial.map(lambda r: (r[0].rsplit("|", 1)[0],) + tuple(r[1:]))   # 소금 제거
         .key_by(lambda r: r[0]).window(...).reduce(merge))                # 2단계
```

> `user_id`를 키로 쓴 덕에 "한 사용자는 늘 같은 작업으로 간다"가 성립해 상위 사용자 판정을
> 작업마다 따로 세어도 된다 (ADR-0010). 단 조회와 장바구니는 토픽이 달라 갈라진다는 것을
> 2026-10-19에 알게 됐다 (ADR-0013).

## 5. 메시지 머리말 (ADR-0005)

### 5-1. 기획이 깨진 지점
기획서는 "Kafka 헤더만 보고 거르기"를 전제했다. 그런데 PyFlink 2.2.1 패키지를 열어 보니
`KafkaSource`에 **`set_value_only_deserializer`만** 있었다. Python에서는 키와 헤더를 읽을 수 없다.

### 5-2. 후보와 선택
| 방식 | 판정 |
| --- | --- |
| **값 앞에 탭으로 구분한 머리말** | **채택.** `split` 한 번으로 읽어 비용이 작음 |
| Table API의 Kafka 메타데이터 열로 헤더를 읽은 뒤 DataStream으로 변환 | 가능하지만 구조가 복잡해짐 |
| Java로 거르기 단계만 작성 | 가장 빠르지만 언어가 두 개가 됨 |

```python
# src/databrain/wire.py
#   user_id \t event_id \t ingest_ms \t {본문 JSON}     ← 이 날의 형식
def peek(value):
    """본문을 파싱하지 않고 머리말만 읽는다 (거르는 단계용, 저비용)."""
    u, e, ts, body = value.split(SEP, 3)
    return Head(u, e, int(ts), body)
```

**거르기 단계는 `peek`만 쓰고, 통과한 이벤트만 `decode`로 본문을 파싱한다.** 이게 설계 원칙 2다.
걸러질 이벤트의 JSON을 파싱하지 않는 것이 비용 절약의 핵심이다.

> 머리말에 `event_ms`가 하나 더 붙는 것은 다음 날(ADR-0007)이다. 그리고 "거르기 비용이
> 무거운 처리의 5%"라는 가정은 'E1에서 측정'으로 미뤄 뒀는데, 2026-10-19에 첫 측정치
> **0.165(가정의 3.3배)**가 나왔다 (ADR-0017).

## 6. 코드로 확인한 PyFlink 제약
구현에 들어가기 전에 패키지를 직접 열어 확인한 것들이다.

| 확인한 것 | 결과 | 영향 |
| --- | --- | --- |
| PyFlink 2.2.1 지원 Python | **3.11/3.12만** | **Python 3.12 고정** (`pyproject.toml`에 박음) |
| `KafkaSource`의 역직렬화 | `set_value_only_deserializer`만 | 머리말 형식 도입 (ADR-0005) |
| `BroadcastProcessFunction` | 있음 | 재시작 없이 비율 변경 가능 |
| `KafkaOffsetsInitializer.timestamp()` | 있음 | 시각 기준 재읽기 가능 |
| `set_bounded()` | 있음 | 밤 재계산에서 '여기까지만' 읽기 가능 |
| `WatermarkStrategy.with_idleness` | 있음 | 유휴 파티션 처리 가능 (설계 원칙 9) |

> **"있다"고 확인한 것이 실제로 작동하는지는 별개였다.** `WatermarkStrategy`는 있었지만
> `from_source`가 Python 시각 추출기를 조용히 무시한다는 것을 다음 날 알게 된다 (ADR-0007).
> **패키지에 함수가 있다 ≠ 그 함수가 내 쓰임에서 동작한다.**

## 7. 이 날 배운 것
1. **구현 전에 종이에서 깨뜨려 본다.** 샘플링 비교 하나로 가설 H2의 성격이 바뀌었다.
   코드를 다 만든 뒤였다면 되돌리기 어려웠다.
2. **같은 결과가 나오는 선택지들 사이에서는 '무엇이 다른가'를 봐야 한다.** 세 제어 알고리즘의
   버린 양이 같았다 → 알고리즘이 아니라 처리 능력이 문제라는 방향 전환으로 이어졌다.
3. **포기한 것을 기록한다.** "Java 대신 Python을 택해 처리량은 상대 비교로만 해석한다"를
   적어 뒀기 때문에 나중에 처리량 숫자를 과신하지 않을 수 있다.
4. **"기능이 있다"를 "작동한다"로 믿지 않는다.** 패키지에 함수가 있어도 내 쓰임에서 무시될 수 있다.
