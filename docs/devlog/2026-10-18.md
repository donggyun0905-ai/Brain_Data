**두 가지 설계가 들어 있다.**

- `.part`로 쓰고 **다 쓴 뒤 이름을 바꾼다** → 끊긴 반쪽 파일이 '완료된 날짜'로 오인되지 않는다

## 2. 이 날의 본체 1 — 제어기가 밀림을 착각했다 (ADR-0008)

### 2-1. 증상
어제(10-17) 전체 흐름 확인에서 남겨 둔 문제가 실제로 터졌다.

> Flink가 이미 다 처리했는데도 제어기는 조회 밀림 **14,821건을 10~15초간 계속 보고**,
> 조회를 **64%까지 쓸데없이 버렸다.**

제어기는 `토픽 끝 위치 − 소비자 그룹 커밋 위치`로 밀림을 계산했다. 그런데 Flink는 **체크포인트가
끝나야** 커밋한다. 커밋 위치는 늘 묵어 있다.

### 2-2. "체크포인트를 자주 하면 되지 않나?" — 아니었다
주기를 바꿔 실측했다 (3회 중앙값, 범위).

| 체크포인트 주기 | 처리량 (건/초) | 커밋이 실제보다 늦은 시간 | 밀림 과대치 | 체크포인트 소요 |
| --- | --- | --- | --- | --- |
| 10초 (당시) | 1,234 (1,151~1,287) | **7.8초** | 11,016건 | 2.7초 |
| 2초 | 1,222 (1,162~1,282) | **7.5초** | 7,000건 | 1.6초 |
| 1초 | 1,260 (1,227~3,280) | **8.8초** | 7,000건 | 0.8초 |

> **체크포인트를 1초로 줄여도 커밋은 7~9초 늦다.**

이유: 부하 중에는 체크포인트 하나가 최대 5~7초 걸린다. 체크포인트 표시가 **밀린 데이터 뒤에
줄을 서기** 때문이다. 주기 단축만으로는 해결되지 않는다.

이때 메모리가 0.7GB 이하로 떨어진 3회(279, 349, 667건/초)는 처리량이 비정상이라 뺐다.
**PC 처리량의 흔들림이 커서 체크포인트 비용 차이는 PC에서 가릴 수 없다**는 것도 기록했다.

### 2-3. 조합 33가지를 시뮬레이션으로 비교했다
`sim/compare_lag_signals.py`를 만들어 신호 13종 · 보정 3종 · 판단 주기를 조합해 비교했다.
**실제 제어 계산 함수(`rate_model.compute_rates`)를 그대로 썼다.** 네 장면에서 돌렸다.

- 덩어리: 평소 20% 부하에 2만 건이 2.7초에 쏟아짐 (10/17 실측 장면)
- 폭증: 평소 50%, 조회 8배 60초
- 하루: 무작위 폭증 3번 + 덩어리 2번 (600초)
- 장애: '하루'와 같되 200~260초 REST 무응답

핵심 결과만 (조회 버림%, 낮을수록 좋다):

| 방식 | 덩어리 | 폭증 | 하루 | 장애 | 신선도 p99 하루/폭증 | 조절 횟수 |
| --- | --- | --- | --- | --- | --- | --- |
| **A0 커밋 10초 (당시 방식)** | 64 | 93 | 83 | 83 | 0.6 / 0.1 | 581 |
| A3 커밋 1초 | 44 | 88 | 66 | 66 | 0.4 / 0.1 | 562 |
| B1 REST 1초 | 42 | 64 | 28 | 35 | 0.1 / 0.1 | 103 |
| D1 커밋 10초 + 추측 항법 | 41 | 60 | 25 | 25 | 0.4 / 0.4 | 99 |
| **G2 REST+ 1초 + 추측 항법 + 대비책 (채택)** | **40** | **59** | **24** | **24** | 0.2 / 0.2 | **97** |
| E6 커밋 10초 + 판단 0.25초 | 64 | 93 | 84 | 84 | 0.2 / 0.1 | **2,301** |

| **Z 실제 위치 (이론상 최선)** | 40 | 59 | 24 | 24 | 0.2 / 0.2 | 97 |

**표를 읽는 법**: 버림은 낮을수록 좋지만 **Z보다 낮으면 처리 능력보다 많이 남긴 것**이라
신선도가 나빠진다 (D6, G4). 처리 능력 자체가 부족한 장면이라 Z도 덩어리 40%, 폭증 59%는 버려야 한다.
당시 방식(A0)은 그보다 **24~59%p를 더** 버렸다.

### 2-4. 알게 된 것
1. **문제의 핵심은 '얼마나 묵었나'이고, 판단을 자주 하는 것은 도움이 안 된다.**
   E6(커밋 + 0.25초 판단)은 조절만 4배(2,301회)로 늘고 버림은 그대로다. **묶은 값을 자주 보는 것**일 뿐이다
2. **커밋 주기 단축(A1~A3)은 부족하다.** 1초로 줄여도 하루 66% (Z는 24%)
3. **추측 항법이 가장 큰 개선이다.** 묵은 커밋(D1)도 Z와 거의 같아진다.
   다만 처리 능력 모델에 기대므로, 모델이 틀리면 위험하다 (D6: 능력 50% 과대추정 → 신선도 4.3초)

세 번째가 중요하다. **추측 항법은 처리 능력 모델을 쓴다.** 그래서 처리 능력을 정확히 아는 것이
단순한 최적화가 아니라 **제어 안정성의 전제**가 된다. (이것이 수면 재생의 가치를 한 번 더 높인다.)

### 2-5. 채택한 방식 (G2)
```python
# src/databrain/controller/main.py
prog = flink.read() if flink else None
if prog is not None:
    pos, moving = prog
    raw = {t: backlog(replace(snaps[t], processed=pos[t])) + moving[t] for t in topics}
    source, age = "flink", args.flink_age          # REST 처리 위치 + 이동 중인 양
else:
    raw = {t: backlog(snaps[t], use_processed=False) for t in topics}
    source, age = "commit", c_age                  # 대비책: 커밋 위치 + 묵은 시간 추정
bc, bv = dead_reckon(model, rates, raw[TOPIC_CART], raw[TOPIC_VIEW], age)   # 추측 항법
```

세 겹이다.
1. **Flink REST `currentOffset`**으로 처리 위치를 읽는다 (커밋보다 훨씬 신선)
2. **이동 중인 양**을 보정한다 (소스는 거르기 단계보다 약 1,000건 앞서 읽는다 — 3회 모두 1,000~1,016건)
3. **추측 항법**으로 그 값이 묵은 시간만큼 앞으로 당긴다

그리고 REST가 안 되면 커밋 위치로 떨어진다 (**대비책**). 장애 장면(200~260초 REST 무응답)에서
24%를 유지한 것이 이 대비책 덕이다.

### 2-6. 함께 고친 것 두 개
**(1) REST 갱신 주기.** Flink REST 지표는 기본 **10초마다** 갱신된다. 1초 제어에 10초 묵은 값을
쓰면 의미가 없다.
```yaml
FLINK_PROPERTIES: |
  metrics.fetcher.update-interval: 1s
```

**(2) 제어기 버전 번호.** 제어기를 다시 켜면 버전이 0부터 시작해서, Flink가 **이미 본 버전보다
작다고 새 비율을 전부 무시**했다. 운영 함정 #5의 반대 경우다.
```python
# 버전은 시작 시각(ms)부터 센다
rates = Rates(version=int(time.time() * 1000))
```

## 3. 이 날의 본체 2 — 상위 사용자 판정 재설계 (ADR-0010)

### 3-1. 무엇이 틀렸나
처음 방식은 Count-Min Sketch(근사 집계)로 "구간 전체 이벤트의 0.1% 이상을 만든 사용자"를 찾았다.

```python
# 버린 코드 (ADR-0010 이전)
class HeavyUserTracker:
    def __init__(self, width=2048, depth=4, share=0.001):
        self.table = [[0.0] * width for _ in range(depth)]
    def is_heavy(self, user_id):
        return self.estimate(user_id) >= self.share * self.total   # 전체의 비율
    def decay(self, factor=0.5):                                   # 10만 건마다 절반
        ...
```

두 가지가 문제였다.
1. **'전체의 비율'이 병렬도에 따라 달라진다.** 작업이 4개면 각 작업의 `total`이 1/4이 되고,
   그러면 문턱값도 1/4이 된다 → **상위 판정이 4~6배로 늘어났다**
2. **절대 건수 기준으로 바꿔도 CMS로는 못 쓴다.** 기준을 20건으로 잡으면, 2048칸 표는
   한 칸에 쌓이는 **잡음만 약 110건**이다. 20건을 세는 데 110건 잡음은 말이 안 된다

### 3-2. 바꾼 방식 — 사용자별 시간 감쇠 건수
```python
# src/databrain/sampling/heavy.py
class HeavyUserTracker:
    def __init__(self, tau_ms=30*60_000, threshold=50.0, prune_every_ms=5*60_000, prune_below=0.05):
        self.users: dict[str, tuple[float, int]] = {}   # user_id → (감쇠 건수, 마지막 이벤트 시각 ms)

    def _value(self, user_id, now_ms):
        v, t = self.users.get(user_id, (0.0, now_ms))
        return v * math.exp(-max(0, now_ms - t) / self.tau)   # 늦게 온 이벤트는 감쇠 없이

    def add(self, user_id, event_ms):
        v = self._value(user_id, event_ms) + 1.0
        self.users[user_id] = (v, max(t, event_ms))
```

바꾼 점 세 가지와 **각각의 이유**:

| 바꾼 것 | 이유 |
| --- | --- |
| 근사 집계(CMS) → **사용자별 정확 집계(dict)** | 절대 건수를 세려면 잡음이 없어야 한다 |
| '전체의 비율' → **절대 건수 50건** | 병렬도와 처리량에 따라 판정이 바뀌면 안 된다 |
| 처리 순서 기준 감쇠 → **이벤트 시각 기준 지수 감쇠** | 배속·따라잡기와 무관하게 같은 판정이 나와야 한다 |

세 번째가 특히 중요하다. 예전 방식은 "10만 건마다 절반"이어서 **재생 배속에 따라 판정이 달라졌다.**
이벤트 시각(`event_ms`)을 쓰면 5배속으로 돌려도 100배속으로 돌려도 같은 결과가 나온다.

메모리는 사용자 수가 기준이다. 11/17 14시 1시간 활동 사용자가 58,033명이고, 작업 하나에
약 10만 명이면 수 MB 수준으로 **추측**했다 (AWS에서 확인 예정). 90분 활동 없는 사용자는
5분마다 지운다 (`prune`).

### 3-3. 실제 데이터에서 알게 된 것
| 기준 | 11/17 이벤트 단위 조회 | 범주·분 오차 p95 | 경로 보존 |
| --- | --- | --- | --- |
| 사용자 해시만 | 0% | 54.3% | 100% |
| 감쇠 30분 20건 | 8.8% | 51.8% | **35.9%** |
| **이상적 기준 (미래를 앎)** | 8.9% | **52.4%** | — |

> **실제 데이터에서는 상위 사용자 처리의 이득이 작다.** 이상적인 기준(미래를 앎)을 써도
> 범주·분 오차가 54.3% → 52.4%로 2%p 줄어드는 정도다. 남은 오차는 거의 다 "적게 남겨서
> 생기는" 표본 오차다.

그리고 "1분 안에 몰아 보는 사용자가 거의 없다" (사용자·분당 조회 최대 13, 시간당 최대 195).
**이 데이터에는 봇이 없다.**

또 하나 바로잡은 것: ADR-0003의 "이벤트 무작위는 퍼널 +16%p 왜곡"은 **가중하지 않은 계산의
결과**였다. "세션이 남을 확률의 역수"로 가중하면 어느 기준에서나 퍼널 오차 p95가 1%p 안팎으로 같다.
사용자 해시가 실제로 지켜 주는 것은 **세션 안의 순서·경로·체류 시간**이다.

## 4. 기준을 20건에서 50건으로 (ADR-0011)

### 4-1. 왜 다시 올렸나
20건에서는 **폭증 날 경로가 36%만 남았다**. 세션 분석(경로·체류·담기 전 조회)이 크게 깨진다.
30건을 검토하다가 40·50·75·100건까지 쟀다.

| 기준 | 이벤트 단위 조회 | 범주·분 오차 p95 | **경로 보존** | 세션 통째 | 체류 틀림 |
| --- | --- | --- | --- | --- | --- |
| 사용자 해시만 | 0% | 54.3% | 100% | 100% | 0% |
| 20건 | 8.8% | 51.8% | **35.9%** | 80.4% | 23.8% |
| 30건 | 2.5% | 53.8% | 62.2% | 94.1% | 7.3% |
| 40건 | 0.8% | 53.8% | 81.6% | 98.3% | 2.2% |
| **50건 (채택)** | **0.3%** | **54.0%** | **92.5%** | **99.5%** | **0.6%** |
| 75건 | 0.0% | 54.3% | 99.6% | 100% | 0% |

**30건부터는 범주·분 오차가 "사용자 해시만"과 범위 안에서 같다.** 정확도 이득은 사라지고
세션 보존만 좋아진다. 그래서 역할을 바꿨다.

> 상위 사용자 처리의 역할을 **"정확도 개선"에서 "봇 같은 극단적 사용자만 잡는 안전장치"**로 바꾼다.

75건 이상은 실제 데이터에서 **아무도 잡지 않아 안전장치가 시험되지 않으므로**, 폭증 날
소수(0.3%)가 잡히는 50건으로 했다. "아무도 안 잡히는 안전장치는 작동하는지 알 수 없다"는 판단이다.

### 4-2. 그럼 왜 아예 빼지 않나 — 가짜 봇을 넣어 시험했다
실제 데이터에 봇이 없으니 **만들어서 넣었다**. `tools/compare_heavy.py`에 봇 주입을 추가했다.


| 경우 | 기준 | 봇 조회 중 이벤트 단위 | 범주·분 오차 p95 |
| --- | --- | --- | --- |
| 11/17 + 봇 20개 × 분당 30건 | 사용자 해시만 | 0% | **70.5% (59.7~74.2)** |
| | **감쇠 30분 50건** | **97.2%** | **53.2% (53.1~53.4)** |
| | 이벤트 무작위만 | 100% | 38.1% |

**봇이 있으면 사용자 해시만으로는 오차가 크게 흔들린다.** 봇이 통째로 들어가면 10배로 부풀려지고,
범위가 15%p 넘게 벌어진다. 50건 기준은 봇 조회의 **97%를 이벤트 단위로 넘겨** 봇이 없을 때
수준(53~54%)으로 되돌린다. **안전장치가 작동한다.**

봇이 적고 느리면(분당 10건) 차이가 작고, 놓친 9%는 **봇이 기준에 닿기까지 처음 약 5분**이다.

> 이것이 중요한 방법론이다. **실제 데이터에 없는 상황은 가짜로 넣어서 시험해야** 안전장치가
> 작동하는지 알 수 있다. 실제 데이터만 보면 "상위 사용자 처리는 쓸모없다"는 잘못된 결론에 이른다.

### 4-3. Flink도 같은 판정을 내리는가
`tools/verify_flink.py`는 **전부 통과(비율 1.0)** 상태라 거르기 규칙을 시험하지 못한다.
그래서 비율을 고정해 두는 `tools/verify_shedding.py`를 따로 만들었다.

```python
p.produce("control.rates", key=b"rates", value=json.dumps(
    {"version": int(time.time()*1000), "cart": 1.0, "view": VIEW_RATE, "at_ms": ...}).encode())
p.flush()
vf.submit("main_job", 1)
```

- 데이터: 11/17 13:50~14:10 실제 158,078건 + 가짜 봇 5개(분당 20건) 2,000건
- 조회 비율 10% 고정, 5배속 실시간 재생
- 정답: 같은 이벤트를 이벤트 시각 순으로 `HeavyUserTracker()` + `keep()`에 넣어 직접 센 값
- **결과 3회 모두: 2,161칸 중 2,161칸 일치, 추정값 불일치 0, 남는 칸 0. 봇 5개 모두 상위 판정**

> **"전부 통과" 검증은 거르기 규칙을 시험하지 못한다.** 비율을 고정해 둔 검증을 따로 만들어야 한다.

## 7. 이 날 배운 것
1. **측정 결과가 늘 0이면 지표가 잘못된 것이다.** 체류 시간 중앙값이 계속 0으로 나와
   "10% 넘게 틀린 세션 비율"로 지표를 바꿨다.
2. **"전부 통과" 검증은 거르기 규칙을 시험하지 못한다.** 비율을 고정해 둔 검증을 따로 만든다.
3. **실제 데이터에 없는 상황(봇)은 가짜로 넣어서 시험해야** 안전장치가 작동하는지 알 수 있다.
   실제 데이터만 보면 "상위 사용자 처리는 불필요"라는 잘못된 결론에 이른다.
4. **판정 기준이 '전체의 비율'이면 병렬도에 따라 흔들린다.** 절대 건수로, 그리고
   **이벤트 시각 기준**으로 세야 배속·따라잡기와 무관해진다.
5. **주기를 줄이는 것으로 안 되는 문제가 있다.** 체크포인트를 10배 자주 해도 커밋은 7~9초 늦었다.
   원인이 '주기'가 아니라 '부하 중 체크포인트 소요'였기 때문이다.
6. **판단을 자주 하는 것은 묵은 값 문제를 못 고친다.** 조절 횟수만 4배로 늘었다.
7. **PC 처리량 흔들림이 커서 PC에서 가릴 수 없는 비교가 있다.** 체크포인트 비용 차이는
   실험 장비로 넘겼다.
8. **실수가 더 나은 자료를 줄 수도 있다.** 10월 대신 11월을 받은 덕에 인공 폭증이 아니라
   실제 블랙프라이데이 폭증으로 검증할 수 있게 됐다.
