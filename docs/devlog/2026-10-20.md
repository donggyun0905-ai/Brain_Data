# 2026-10-20 — 사라진 칸 626개의 정체, 그리고 낙관적으로 보고하던 오차

> 그날 나온 ADR: 0018(사라진 칸)
>
> Docker를 띄우지 않고 **원본 Parquet과 재생 시간표만으로** 어제의 의문을 풀었다.
> 그 과정에서 내 검증 도구가 오차를 낙관적으로 보고하고 있던 것을 찾았다.

## 0. 이 날의 줄거리
어제 전체 흐름 검증에서 닫힌 조회 칸 3,056개 중 ClickHouse에 **2,430개만** 도착했다.
일지에 "작은 칸이 전부 걸러져서일 것으로 **추측**"이라 적고 넘겼다.

데이터 파이프라인에서 **'걸러져서 없는 것'과 '잃어버린 것'을 구분하는 것은 타협할 수 없다.**
그래서 이 날 첫 일로 확인했다. 결론은 "걸러져서 없는 것"이었지만, 확인하는 동안
**더 중요한 것**이 나왔다 — 내가 오차를 좋아 보이게 세고 있었다.

## 1. Docker 없이 확인할 수 있었다

아침에 보니 PC가 꺼졌다 켜져서 Docker 엔진이 내려가 있었다. 그런데 **어제 추가한
판단 기록 파일 3개가 남아 있었다.**

```
data/runs/decisions-20261019-140238.tsv
data/runs/decisions-20261019-141742.tsv
data/runs/decisions-20261019-141011.tsv
```

어제 "기록을 잃어 실험을 다시 돌렸다"는 일을 겪고 넣은 안전장치가 바로 값을 했다.
그리고 이번 질문은 판단 기록조차 필요 없었다 — **재생 시간표와 원본 Parquet만으로** 풀렸다.

## 2. 첫 계산에서 두 번 틀렸다

### 2-1. DuckDB의 `/`는 실수 나눗셈이다
데이터 분 단위로 묶으려고 이렇게 썼다.

```sql
-- 틀린 코드
(epoch(event_time) - (SELECT epoch(min(event_time)) FROM ...))::bigint / 60 AS dmin
```

칸이 **57,759개**로 나왔다. 3,056개여야 하는데 19배다. `::bigint` 뒤의 `/`가 정수 나눗셈이
아니라 실수 나눗셈이라 `dmin`이 소수가 됐고, 그래서 거의 모든 이벤트가 자기 칸을 가졌다.

```sql
-- 고친 코드
floor((epoch(event_time) - epoch((SELECT s FROM t0))) / 60)::bigint AS dmin
```

> 숫자가 예상보다 **한 자리 이상** 다르면 계산식을 먼저 의심한다. 19배는 "데이터가 그렇구나"가
> 아니라 "내가 틀렸구나"다.

### 2-2. "가장 작은 626개"는 틀린 가정이었다
처음엔 "누락 칸 = 가장 작은 칸 626개"라고 보고 그 칸들이 쥔 조회를 셌다 → **1,222건(0.60%)**.
"거의 아무것도 안 잃었다"는 결론으로 갈 뻔했다.

실제 누락 칸이 쥔 조회는 **8,177건(4.0%)**이었다. 누락 칸은 '가장 작은 칸'이 아니라
**'폭증 구간의 칸'**이고, 폭증 구간 칸은 중간 크기도 많다 (사용자 수 중앙 8명).

> 틀린 가정이 **6.7배** 낙관적인 숫자를 만들었다. 가정은 세우되 **관측으로 확인**해야 한다.

## 3. 확인: 데이터 손실이 아니다

### 3-1. 어느 구간이 세게 걸렸나 — 재생 시간표로 안다
폭증 주입은 `--burst 600,600,6`이었다. 데이터 시각 600~1200초를 6배로 압축한다.

```python
wall = build_wall_clock(5.0, [(600.0, 600.0, 6.0)])
#   데이터 분  5: 벽시계  60.0~ 72.0초  (길이 12.0초)   ← 평시
#   데이터 분 10: 벽시계 120.0~122.0초  (길이  2.0초)   ← 폭증 (6배 압축)
#   데이터 분 19: 벽시계 138.0~140.0초  (길이  2.0초)
#   데이터 분 20: 벽시계 140.0~152.0초  (길이 12.0초)   ← 회복
```

**데이터 분 10~20이 세게 걸린 구간**이다. 제어기 로그를 안 봐도 시간표만으로 알 수 있다.

```
닫힌 칸 3,056 = 폭증 구간(분 10~20) 1,163 + 평시 1,893
평시는 통과 비율이 1.0이라 사라질 칸이 없다
```

### 3-2. 사라질 확률은 손으로 계산된다
사용자 해시 샘플링에서는 **한 사용자가 통째로 들어오거나 빠진다.** 그래서 한 칸이 사라질 확률은

```
P(그 칸이 사라짐) = (1 − 통과비율) ^ (그 칸의 서로 다른 사용자 수)
```

폭증 구간 칸의 사용자 수는 중앙 8명이다. 비율 0.04면 `0.96^8 = 0.72` — **중간 크기 칸도
72% 확률로 사라진다.** 이래서 "가장 작은 칸만 사라진다"는 가정이 틀렸다.

| 폭증 구간 통과 비율 | 사라질 칸 | 그 칸들이 쥔 조회 | 전체 대비 |
| --- | --- | --- | --- |
| 0.02 | 849 | 13,439 | 6.56% |
| **0.04** | **705** | **8,309** | **4.06%** |
| 0.05 | 652 | 6,910 | 3.37% |
| 0.10 | 477 | 3,419 | 1.67% |
| **관측** | **626** | **8,177** | **4.0%** |

**칸 수와 이벤트 수가 둘 다 맞는다.** 어느 하나만 맞으면 우연일 수 있지만 둘 다 맞으면
기구가 설명된 것이다. 제어기가 폭증 중 1.0 → 0.02까지 쓸어내렸다 올라왔으므로 그 구간
실효 비율이 0.04~0.05인 것도 자연스럽다.

→ **데이터 손실이 아니다. 그 칸의 모든 사용자가 걸러져 행이 안 생긴 것이다.**

## 4. 이 날의 본체 — 내가 오차를 좋아 보이게 세고 있었다

### 4-1. 무엇이 문제였나
어제 만든 `accuracy()`는 이렇게 비교했다.

```python
# 문제 있는 코드
seen = [k for k in want if k in got]        # ClickHouse에 있는 칸만
t_tot = sum(want[k] for k in seen)          # 정답도 그 칸만
e_tot = sum(got[k][0] for k in seen)
return {"추정 오차%": (e_tot - t_tot) / t_tot * 100}
```

사라진 칸을 **분모와 분자에서 함께 뺐다.** 그러면 "사라진 것"이 오차에 전혀 안 잡힌다.

| 기준 | 3회 중앙값 (범위) |
| --- | --- |
| 있는 칸만 (어제 보고한 값) | **+0.42%** (0.27~0.51) |
| **전체 정답 기준** | **−3.58%** (−3.73~−3.36) |

둘 다 작은 값이지만 **뜻이 다르다.**
- `+0.42%` = "화면에 뜬 칸의 숫자는 믿을 만하다" → 참이고 쓸모 있는 정보
- `−3.58%` = "화면의 범주를 다 더해도 실제 총량보다 3.6% 모자라다" → **사용자가 겪는 것**

어제 나는 앞의 숫자만 보고했다. 틀린 값은 아니지만 **고른 쪽이 낙관적이었다.**

### 4-2. 고친 것
```python
def accuracy(day="data/sub/ctl30") -> dict:
    """**두 가지 오차를 모두 낸다** (2026-10-20에 고침). ..."""
    seen    = [k for k in want if k in got]
    missing = [k for k in want if k not in got]
    t_all, t_seen = sum(want.values()), sum(want[k] for k in seen)
    return {..., "사라진 칸": len(missing),
            "사라진 칸이 쥔 조회": sum(want[k] for k in missing),
            "추정 오차%(있는 칸만, 낙관적)": (e_tot - t_seen) / t_seen * 100,
            "추정 오차%(전체 정답 기준)": (e_tot - t_all) / t_all * 100}
```

이름에 **'낙관적'**을 박았다. 나중에 표를 다시 볼 때 어느 쪽을 보고 있는지 헷갈리지 않게.

> 어제 ADR-0016에 "틀린 판정보다 판정 불가가 낫다"를 적었는데, 이것은 같은 성격의 다른 규칙이다.
> **지표를 하나만 내면 낙관적인 쪽을 고르게 된다.** 둘 다 낸다.

## 5. H2의 빈틈을 찾았다

ADR-0015에서 H2 기준 ①("표시한 95% 오차 범위가 실제값을 95% 안팎으로 포함")을 재고 통과시켰다.
그 측정은 **ClickHouse에 행이 있는 칸**만 대상으로 한다.

> **행이 없는 칸에는 오차 범위를 붙일 수조차 없다.**

"보이는 것의 오차는 정직하다"는 참이지만 **"보이지 않는 것"은 표현되지 않는다.**
통과 비율 0.04에서 폭증 구간 칸의 **54%(626/1,163)**가 아무것도 남기지 않는다.
오차 범위로는 가려지지 않는 별개의 빈틈이다.

### 제안한 해결 (ADR-0018)
**분 단위 합계 행을 따로 내보낸다.**

범주를 더해 합계를 만들면 사라진 칸만큼 모자란다. 그런데 **분 단위 전체 합계는 사라지지 않는다** —
한 분에는 사용자가 수천 명이라 `(1 − 비율) ^ 수천 ≈ 0`이다.

그래서 `main_job.py`가 `view|__all__` 같은 키로 범주를 섞지 않은 분 합계를 하나 더 내보내면
**화면의 총량은 거르기와 무관하게 맞는다.** 범주별 숫자는 여전히 사라질 수 있지만,
그건 "이 분의 범주 N개 중 M개는 표본에 하나도 안 걸렸습니다"로 **표시하면 된다.**
숫자를 숨기지 않는 것이 H2('정직한 정확도')의 뜻이다.

버린 대안: "사라진 칸을 0이 아니라 '모름'으로 표시하고 합계에서 제외" → 그러면 화면에 총량을
띄울 수 없다. 총량은 쓸 수 있어야 한다.

## 6. 이 날 배운 것
1. **숫자가 예상과 한 자리 이상 다르면 데이터가 아니라 계산식을 의심한다.** 칸이 19배로 나온 것은
   DuckDB의 `/`가 실수 나눗셈이어서였다.
2. **가정은 세우되 관측으로 확인한다.** "누락 칸 = 가장 작은 칸"이라는 틀린 가정이 6.7배
   낙관적인 숫자(0.60% vs 4.0%)를 만들었다.
3. **기구를 설명했다고 말하려면 두 가지 이상이 맞아야 한다.** 칸 수만 맞으면 우연일 수 있다.
   칸 수와 이벤트 수가 함께 맞아서 설명이 됐다.
4. **지표를 하나만 내면 낙관적인 쪽을 고르게 된다.** 둘 다 내고, 이름에 '낙관적'을 박아 둔다.
5. **검증은 꼭 스택을 띄워야 하는 게 아니다.** 재생 시간표와 원본만으로 Docker 없이 풀렸다.
   "무엇이 참이어야 하는가"를 먼저 계산하면 실험이 줄어든다.
6. **어제의 안전장치가 오늘 값을 했다.** 판단 기록을 파일로 남겨 둔 덕에 PC가 꺼졌어도
   어제 자료가 살아 있었다.
