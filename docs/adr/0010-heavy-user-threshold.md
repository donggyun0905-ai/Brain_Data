# ADR-0010: 상위 사용자 기준은 "30분 감쇠 건수 20건 이상" (이벤트 시각 기준, 정확 집계)

- 날짜: 2026-10-18 / 상태: 채택 (기준값 20건은 ADR-0011에서 50건으로 바꿈) / 관련: ADR-0003 (혼합 샘플링), ADR-0011

## 상황
혼합 샘플링(ADR-0003)은 상위 사용자만 이벤트 단위로 거른다. 기존 기준은 Count-Min Sketch로 센
"구간 전체 이벤트의 0.1% 이상"이었고, 10만 건마다 절반으로 줄였다. 이 기준을 실제 11월 데이터로 확인했다.

## 실측 (실제 11월 데이터)
- 1분 안에서는 몰아 보는 사용자가 거의 없다. 사용자·분당 조회는 중앙값 1, p99 4, **최대 13** (11/17 14시).
  ADR-0003 시뮬레이션(파레토 분포 가정)보다 꼬리가 훨씬 얇다
- 1시간 단위에서는 차이가 보인다. 시간 상위 1%의 기준은 49건(11/17), 32건(11/5), 최대 195건
- **기존 기준의 문제**
  - 기준이 필터 작업 하나가 본 양의 0.1%라서, 병렬도가 바뀌면 같이 바뀐다.
    병렬 1에서 4로 늘리면 상위로 판정되는 조회가 0.3%에서 6.4%로(11/17), 4.3%에서 26.7%로(11/5) 늘었다
  - 10만 건마다 줄이므로, 기억하는 기간이 처리량과 배속에 따라 달라진다

1분 총량 오차(p95)는 11/17 기준 사용자 해시만 9.3%, 채택 기준 9.1%, 이벤트 무작위만 7.1%이다.
기준끼리의 차이가 시드 묶음 사이 흔들림(약 ±1%p)보다 작아서, 1분 총량으로는 기준을 가를 수 없다.
비율 20%와 5%에서도 순서는 같다.

## 알게 된 것
1. **실제 데이터에서는 상위 사용자 처리의 이득이 작다.** 이상적인 기준(미래를 앎)을 써도
   범주·분 오차가 54.3%에서 52.4%로 줄어드는 정도다. 남은 오차는 거의 다 "적게 남겨서 생기는" 표본 오차다
2. 나머지 기준들은 모두 한 줄 위에 있다. 이벤트 단위로 넘기는 양을 늘리면 오차가 줄고, 쪼개지는 세션이 늘어난다.
   상위 사용자 기준은 이 줄의 어디에 설지를 고르는 다이얼이다
3. 이상적 기준과 가장 비슷한 것은 "감쇠 30분 20건"이다. 상위 판정 조회가 8.8%(이상적 기준 8.9%)이고 오차도 같다.
   세션 대부분을 지키면서(쪼개짐 2.3%) 몰아 보는 사용자(봇 추정)만 이벤트 단위로 넘긴다
4. 퍼널(조회 세션 중 장바구니 세션 비율)은 "세션이 남을 확률의 역수"로 가중하면 어느 기준에서나 오차 p95가 1%p 안팎이다.
   ADR-0003의 "이벤트 무작위는 퍼널 +16%p 왜곡"은 가중하지 않은 계산의 결과였다.
   사용자 해시가 실제로 지켜 주는 것은 세션 안의 순서·경로·체류 시간이다 (이번에는 재지 않음)
5. 통과 비율 10%에서 (범주, 1분) 칸 오차 p95는 어느 방식이든 39~54%다. 칸 단위로 2% 정확도는 불가능하다.
   이는 H2(표시한 오차 범위의 적중률)의 근거를 더해 준다

## 결정
- 상위 사용자 판정 방식
  - 사용자별 **지수 감쇠 건수**를 쓴다: 시간 상수 30분, 기준 20건 이상.
    꾸준히 보는 사용자로 치면 시간당 약 40건 이상이다
  - 시간은 이벤트 시각(머리말의 event_ms)으로 잰다
  - 사용자별로 정확히 센다 (dict). 오래 쉰 사용자(감쇠 건수 0.05 미만, 약 90분 동안 활동 없음)는 5분마다 지운다
- 이렇게 하면 판정이 병렬도·처리량·배속·따라잡기와 무관해진다.
  Kafka 키가 user_id라서 한 사용자는 늘 같은 필터 작업으로 간다 → 작업마다 따로 세어도 정확하다
- Count-Min Sketch는 버린다
  - 기준을 절대 건수 20으로 잡으면, 2048칸 표는 한 칸에 쌓이는 잡음만 약 110건이라 쓸 수 없다
  - 정확히 세면 기억할 사용자 수가 메모리 기준이다. 11/17 14시 1시간 활동 사용자가 58,033명이고,
    작업 하나에 약 10만 명이면 수 MB 수준이다 (추측, AWS에서 확인)

## 세션 지표 추가 측정 (2026-10-18, 같은 도구·조건, 통과 비율 10%)
조회가 하나라도 남은 세션만 본다. 움직이는 설명 페이지: docs/sampling-cctv.html

| 기준 | 11/17 세션 통째 보존 | 11/17 경로 보존 | 11/17 체류 시간 10% 넘게 틀림 | 11/17 담기 전 조회 보임 | 11/5 경로 보존 |
| --- | --- | --- | --- | --- | --- |
| 사용자 해시만 | 100% | 100% | 0% | 100% | 100% |
| 이벤트 무작위만 | 8.8% | 1.4% | 95.0% | 42.4% | 1.6% |
| 감쇠 30분 20건 (현재) | 80.4% | 35.9% | 23.8% | 69.6% | 57.8% |
| 감쇠 30분 30건 | 94.1% | 62.2% | 7.3% | 86.8% | 87.0% |
| 감쇠 60분 40건 | 95.6% | 67.6% | 5.6% | 89.6% | 89.8% |

- 세션 기준으로 보면 많이 보는 사용자가 경로(A→B)의 대부분을 만든다. 상위 8.8%의 조회를 이벤트 단위로 넘기면 경로의 64%가 끊긴다
- 20건 → 30건: 범주·분 오차 51.8% → 53.8%(+2%p), 경로 보존 35.9% → 62.2%(+26%p)
- **재검토 결과**: 40·50건까지 재 보니 30건부터는 정확도가 사용자 해시만과 같고 세션 보존만 계속 좋아졌다 → 50건으로 바꿈 (ADR-0011)

## 영향
- `sampling/heavy.py`의 `HeavyUserTracker(tau_ms, threshold)`가 `add(user_id, event_ms)`를 받는다.
  `main_job.py`의 10만 건 감쇠는 삭제
- 남은 일
  - 세션 안 순서·경로 지표가 필요한지 결정한다. 필요 없다면 이벤트 단위를 더 넓히는 것이 오차 면에서 낫다 (결과 표 참고)
  - E3에서 같은 도구로 다른 날·시간을 확인한다
