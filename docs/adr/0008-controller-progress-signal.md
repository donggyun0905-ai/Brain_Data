# ADR-0008: 제어기는 Flink REST 처리 위치 + 추측 항법으로 밀림을 잰다 (커밋 위치는 대비책)

- 날짜: 2026-10-18 / 상태: 채택 / ADR-0002 보완, ADR-0007 '남은 문제' 해결

## 상황
제어기는 '토픽 끝 위치 - 소비자 그룹 커밋 위치'로 밀림을 계산했다.
그런데 Flink는 체크포인트가 끝나야 커밋하므로 커밋 위치는 늘 묵어 있다.
2026-10-17 전체 흐름 확인에서 Flink가 이미 다 처리했는데도 제어기는 조회 밀림 14,821건을
10~15초간 계속 보고, 조회를 64%까지 쓸데없이 버렸다.

## 실측 (PC 가벼운 설정, 6만 건 몰아넣기, 체크포인트 주기별 3회 중앙값과 범위)

| --- | --- | --- | --- | --- |
| 10초 (지금) | 1,234 (1,151~1,287) | 7.8초 (7.0~8.3) | 11,016건 (10,000~11,016) | 2.7초 |
| 2초 (2회) | 1,222 (1,162~1,282) | 7.5초 (7.3~7.8) | 7,000건 | 1.6초 |

- 메모리가 0.7GB 이하로 떨어진 때의 3회(279, 349, 667건/초)는 처리량이 비정상이라 뺐다.
  PC 처리량은 흔들림이 커서 체크포인트 비용 차이는 PC에서 가릴 수 없다 → 실험 장비에서 다시
- **체크포인트를 1초로 줄여도 커밋은 7~9초 늦다.** 부하 중에는 체크포인트 하나가 최대 5~7초 걸리기 때문
  (체크포인트 표시가 밀린 데이터 뒤에 줄을 섬). 주기 단축만으로는 해결되지 않는다
- 위치 조회 속도: 파티션마다 따로 요청(지금) 15~50ms, 가끔 210ms / 관리 API 일괄 요청 2~3ms / Flink REST 5~25ms
- Flink REST 소스 위치(currentOffset)는 기본 설정에서 **10초마다** 갱신된다 (`metrics.fetcher.update-interval`)
- 소스는 거르기 단계보다 약 1,000건 앞서 읽는다 (Python 묶음 처리, 3회 모두 1,000~1,016건)

### 알게 된 것
1. **문제의 핵심은 '얼마나 묵었나'이고, 판단을 자주 하는 것은 도움이 안 된다.** E6(커밋 + 0.25초 판단)은
   조절만 4배로 늘고 버림은 그대로다. 묵은 값을 자주 보는 것일 뿐이다
2. **커밋 주기 단축(A1~A3)은 부족하다.** 1초로 줄여도 하루 66% (Z 24%). 실측에서도 커밋이 7~9초 늦다
3. **추측 항법이 가장 큰 개선이다.** 묵은 커밋(D1)도 Z와 거의 같아진다. 다만 처리 능력 모델에 기대므로
   능력을 50% 높게 잡으면 신선도 p99가 4.3초로 목표(5초)에 붙는다(D6). 신선한 REST와 함께 쓰면 1.1~1.7초(G4, D7)
4. 신호 주기는 1초면 충분하다. 0.25초(B2, F1)는 1초 + 추측 항법(D4, G2)보다 낫지 않다
5. 이동 중 양 보정(REST+)과 작은 밀림 무시는 효과가 작다 (실제 처리 능력이 크면 1,000건의 비중은 더 작아짐)
6. 진행 토픽(C)은 REST와 성능이 같고 장애에도 강하지만, Flink 작업 코드를 고쳐야 하고 데이터가 멈추면 마지막 값이 갱신되지 않는다
7. 판단 0.5초 + 빠른 상승(G3)은 1~2%p 덜 버리지만 조절 횟수가 1.6배다 → E1 측정 뒤 다시 판단

## 결정 (G2)
1. 처리 위치: **Flink REST 소스 currentOffset(+1)**. 작업 관리자 지표 수집 주기 `metrics.fetcher.update-interval: 1s`
2. 측정 지점 하나 추가: 소스가 내보낸 수 + 제어 메시지 수 - 거르기 단계가 받은 수 = 이동 중인 양을 밀림에 더함
3. **추측 항법**: 측정이 묵은 시간(REST 0.5초, 커밋은 마지막 변화 후 경과 + 2초) 동안 처리 능력 모델로 처리했을 양을 뺌.
   Flink가 멈춰도 밀림을 0으로 착각하지 않도록 경과 시간은 15초까지만 반영
4. **대비책**: REST가 응답하지 않거나 작업이 없으면 커밋 위치 + 추측 항법
5. 끝 위치·커밋 위치는 관리 API 일괄 요청 (15~210ms → 2~3ms)
6. 판단 기록(log.decisions, ClickHouse decisions)에 측정값, 신호 출처(flink/commit), 묵은 시간을 남김
7. `--signal commit`으로 예전 방식을 그대로 돌릴 수 있게 둔다 (E1 비교 실험용)

탈락: 커밋 주기 단축만(A, 효과 부족·체크포인트 비용), 진행 토픽(C, 작업 코드 변경 대비 이득 없음),
판단 주기 단축만(E, 조절만 늘어남), Prometheus(15초, 설계 원칙 4)

## 실제 확인 (2026-10-18, PC, 가짜 데이터 2만 건을 2.7초에 몰아넣기, 처리 능력 1,250 설정, 3회 중앙값과 범위)
| | 커밋 (예전) | REST + 추측 항법 (새) |
| --- | --- | --- |
| 거르기 단계 통과율 | 8.4% (6.2~8.4) | 21.4% (10.6~35.6) |
| Flink가 다 처리한 뒤에도 밀림이 있다고 본 시간 | 8초 (8~8) | **0초 (0~0)** |
| 다 처리한 뒤 조회 비율이 100%로 돌아오기까지 | 17초 (17~17) | 5초 (4~6) |
| 제어기가 본 최대 조회 밀림 | 18,453 (18,453~18,453) | 13,530 (7,346~16,410) |

- 새 방식도 덩어리 직후에는 조회를 2%까지 줄인다. 처리 능력 1,250건/초로 2만 건을 2초 안에 비울 수 없으니 맞는 판단이다
- 대비책(커밋)은 각 회 첫 판단 1번에만 쓰였다 (작업 시작 직후 파티션 지표가 아직 없을 때)
- 회복 시간 5초는 상승 폭 제한(0.1/초) 때문이다. G3 설정은 E1 측정 뒤 결정

## 함께 고친 것
- 제어기를 다시 켜면 버전이 0부터 시작해, Flink가 이미 본 버전보다 작아 새 비율을 전부 무시하는 문제
  → 버전을 시작 시각(ms)부터 센다
- `FLINK_PROPERTIES` 블록 안의 `#` 주석을 Flink가 값으로 읽어 작업 관리자가 시작에 실패하는 문제 (기본 compose에도 있었음)
- `main_job.py`의 체크포인트 주기를 환경 변수 `CHECKPOINT_MS`로 바꿀 수 있게 함 (기본 10초 유지)

## 남은 것
- 처리 능력 모델이 틀리면 추측 항법도 틀린다 (G4, G5). 수면 재생이 고치는 값이 곧 이 숫자다 → 1~2월
- 실험 장비(AWS)에서 체크포인트 비용과 G3 설정 다시 측정
