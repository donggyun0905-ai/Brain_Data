# ADR-0002: 예측형 + 되먹임 제어기, 밀림은 Kafka에서 직접 읽기

- 날짜: 2026-10-16 / 상태: 채택

## 상황
폭증 시 대시보드 신선도 p99 5초 이내를 지키면서 버리는 데이터를 최소화해야 한다.

## 비교 (sim/compare_controllers.py, 조회 10배 폭증)
| 알고리즘 | 신선도 p99 | 조회 버린 비율 | 조절 횟수 |
| --- | --- | --- | --- |
| 단계형 | 1.9초 | 58% | 16 |
| AIMD | 1.9초 | 57% | 36 |
| 예측형 + 되먹임 | 0.1초 | 58% | 24 |

처리 능력을 20% 낮게 / 20% 높게 / 50% 높게 잘못 추정해도 신선도 0.1 / 0.4 / 0.9초.

## 결정
- 예측형 + 되먹임 채택. 단계형은 비교 대상으로 유지
- 밀림은 Kafka 관리 API로 1초마다 직접 계산. Prometheus(기본 15초)는 화면용
- 비율 신호에는 버전 번호를 붙이고, Flink는 더 높은 버전만 적용

## 보완 (2026-10-18, ADR-0008)
'Kafka에서 직접 계산'의 처리 위치로 커밋 위치를 쓰면 실측 7~9초 묵어서 조회를 필요보다 24~59%p 더 버린다.
처리 위치는 Flink REST(1초)에서 읽고 추측 항법으로 묵은 시간을 보정한다. 커밋 위치는 대비책

## 발견
버린 양은 알고리즘과 무관하게 처리 능력이 정한다 → 수면 재생은 문턱값이 아니라 처리 능력 모델을 고친다 (→ **ADR-0014**. 0006번은 다른 주제에 쓰였다)
