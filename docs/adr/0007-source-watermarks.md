# ADR-0007: 워터마크는 Flink SQL Kafka 소스에서 파티션별로 만든다

- 날짜: 2026-10-17 / 상태: 채택 / ADR-0005를 보완 (머리말에 event_ms 추가)

## 상황
가짜 데이터(REES46 형식, 10분, 2,020건)를 Kafka에 먼저 넣고 Flink 작업을 나중에 띄워
밀린 데이터를 따라잡게 했더니, 메인 작업의 1분 집계가 정답과 크게 달랐다.
(닫힌 창 70개 중 대부분이 틀림. 밀림은 0이라 데이터는 다 읽었는데 집계에서 빠짐)

원인은 두 가지였다.
1. 워터마크를 Kafka에서 읽은 **뒤** 합친 흐름에 붙였다. 밀린 데이터를 읽을 때 Kafka 리더는
   파티션 하나를 몇 분치씩 몰아 읽으므로 합친 흐름의 시각이 뒤섞이고, 앞서 나간 워터마크 때문에
   다른 파티션 이벤트가 '늦음'으로 버려진다. 밀렸다가 따라잡는 상황은 이 프로젝트의 핵심 장면이다.
2. 소스에 넘긴 Python `TimestampAssigner`는 PyFlink 2.2.1 `from_source`에서 **오류 없이 무시**된다.
   워터마크가 2019년이 아니라 Kafka 기록 시각(2026-10-17)으로 잡히는 것을 REST API로 확인했다.

## 후보
| 방식 | 판정 |
| --- | --- |
| 합친 흐름에 워터마크 (기존) | 탈락. 따라잡기 중 데이터 손실 |
| from_source + Python 시각 추출기 | 탈락. PyFlink가 추출기를 무시함 |
| Kafka 기록 시각을 이벤트 시각(2019년)으로 보냄 | 탈락. 7일 시간 보관 규칙이 즉시 지움 (설계 원칙 7과 충돌) |
| 소스 병렬도를 파티션 수만큼 올리고 소스 직후에 워터마크 | 탈락. 조회 토픽 12개 → 메모리 부족 |
| **Flink SQL Kafka 소스에서 머리말의 event_ms로 WATERMARK 선언 → to_data_stream** | **채택** |

## 결과
- 머리말 형식: `user_id \t event_id \t event_ms \t ingest_ms \t {본문 JSON}` (event_ms 추가)
- `flink_jobs/watermarks.py`: SQL 계산 열 `SPLIT_INDEX(v, TAB, 2)`로 event_ms를 꺼내 파티션별 워터마크
  (순서 뒤바뀜 5초, 유휴 시간 10초 `table.exec.source.idle-timeout`). 계산은 Java 쪽에서 하므로 Python 비용 없음
- 제어 토픽은 워터마크를 내지 않고 0.5초 유휴 시간만 둔다. 계속 비워두면 창이 안 닫히고,
  현재 시각을 내면 재생 중인 과거 데이터가 '늦음'이 될 수 있기 때문
- 확인 (2026-10-17, 가짜 데이터, 1회):
  - 따라잡기 상황에서 메인 70/70, 구매 19/19 창이 DuckDB 정답과 일치
  - 조회 비율 30% 신호를 보낸 뒤 2만 건 재생: 조회 29.7% 통과, 1/비율 추정 오차 -0.9%, 장바구니 100%, 빠진 창 0
- 실제 데이터와 3회 반복 측정은 11월 실행 검증 때 다시 한다
  → 2026-10-18 실제 데이터(REES46 11/17 피크 5분치, 37,766건)로 확인 (`tools/verify_flink.py`):
    실시간(5배속) 3회, 따라잡기(30배속으로 다 쌓은 뒤 작업 시작) 3회 모두 메인 619/619, 구매 436/436 창 일치
- 함께 발견: Flink 출력(agg.*)의 Kafka 기록 시각이 이벤트 시각(2019년)으로 붙는다 → 7일 보관 규칙에 바로 지워질 수 있음.
  집계 토픽은 `message.timestamp.type=LogAppendTime`으로 브로커가 받은 시각을 쓰게 함
