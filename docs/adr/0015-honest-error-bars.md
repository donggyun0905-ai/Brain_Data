# ADR-0015: 오차 범위 계산 방식과 H2 성공 기준 실측 (기준 ③은 달성 불가)

- 날짜: 2026-10-19 / 상태: 채택 (분산 식), **기획서 갱신 요청** (기준 ③)

## 상황
기획서의 H2(정직한 정확도) 성공 기준은 세 개다.

> ① 화면에 표시한 95% 오차 범위가 실제값을 95% 안팎으로 포함
> ② 퍼널 전환율 편향 1%p 이내
> ③ 통과 비율 10% 이상에서 5분 단위 조회수 오차 3% 이내

시뮬레이션 예측란에 **"③은 실측 필요"**로 남아 있었고, ①을 계산하는 코드는 **아예 없었다.**
②는 `tools/compare_heavy.py`가 이미 재고 있다 (통과 10%에서 퍼널 p95 0.8~1.2%p).

## 분산 식 — 묶음 추출로 보면 더해지는 형태가 된다
혼합 샘플링은 상위 사용자는 이벤트 단위(독립), 나머지는 사용자 단위(통째로)다.
단순 이항 분산을 쓰면 구간이 좁다 (측정: 통과 10%에서 적중률 **80% 미만**, `tests/test_interval.py`).

'묶음'을 `상위 사용자의 이벤트 하나` 또는 `(일반 사용자, 통과 비율)별 이벤트 뭉치`로 잡으면

    분산 V = Σ_c A_c² (1 − r_c) / r_c         (A_c = 묶음 크기)
    남긴 것만으로 재는 값 V^ = Σ_{남은 c} A_c² (1 − r_c) / r_c²

A² 은 묶음의 i번째에서 `2i − 1`을 더하면 만들어지므로(1+3+5+…=A²), 남긴 이벤트마다

    흔들림 조각 = (2·묶음_안_순번 − 1) × (1 − 비율) / 비율²

을 실어 보내고 칸마다 **더하면** 된다. `est_count`를 더하는 것과 같은 모양이라
집계 단계(`flink_jobs/main_job.py`의 `merge`)에 숫자 하나만 늘리면 끝이다.
구현: `src/databrain/sampling/interval.py`, 테스트 12개.

## 실측 (11/17 14시, 조회 433,606건, 실제 100건 이상인 칸만. 12회 × 3묶음, 중앙값과 범위)

| 창 | 통과 비율 | 적중률% (기준 ①) | 창 총량 오차 p95% (기준 ③) |
| --- | --- | --- | --- |
| 1분 | 50% | 94.7 (94.3~94.8) | 3.3 (3.1~3.7) |
| 1분 | 20% | 93.5 (93.5~93.6) | 6.3 (6.2~6.5) |
| 1분 | 10% | 91.9 (91.9~92.5) | 9.7 (9.5~9.8) |
| 5분 | 50% | 93.1 (93.1~93.3) | 2.3 (2.2~2.7) |
| 5분 | 20% | 90.2 (90.0~90.6) | 4.7 (4.3~4.8) |
| **5분** | **10%** | **86.0 (86.0~86.4)** | **7.2 (6.6~7.4)** |

### 기준 ③: 달성 불가
목표는 '통과 10%에서 5분 단위 3% 이내'인데 실측은 **7.2%**로 2.4배다.
3%는 통과 비율 약 50%에서나 지켜진다 (2.3%). 통과 20%에서도 4.7%로 넘는다.

오차는 남은 건수의 제곱근에 반비례하므로, 통과 10%에서 3%를 맞추려면 창이 약 5.8배
(≈ 30분) 필요하다 — **추측**이다. 1시간 데이터로는 30분 창이 2개뿐이어서 p95를 낼 수 없고,
여러 시간을 이어 붙여 다시 재야 확인된다.

### 기준 ①: 식은 맞고, 추정이 원인
정답 분산(모든 묶음을 다 안다고 가정)으로 구간을 만들면 적중률이 어디서나 목표에 있다.
같은 조건에서 남긴 표본만으로 추정하면 창이 커질수록 벌어진다.

| 창 | 통과 | 추정 분산 적중률 | **정답 분산 적중률** | 차이 |
| --- | --- | --- | --- | --- |
| 1분 | 50% | 94.8% | 95.3% | 0.5%p |
| 1분 | 10% | 92.5% | 94.3% | 1.8%p |
| 5분 | 20% | 90.2% | 95.4% | 5.2%p |
| 5분 | 10% | 86.0% | **95.5%** | **9.5%p** |

즉 정규 근사나 겹치는 임계값의 포개짐 때문이 아니다. `V^`는 기대값은 맞지만
**분포가 오른쪽으로 치우쳐** 있어 절반 넘는 경우에 정답보다 작게 나온다.
묶음 크기가 들쭉날쭉할 때(한 사람이 5분 동안 수십 건) 큰 묶음은 대개 안 뽑히므로
`V^`가 그 몫을 놓친다. 창이 커질수록 묶음 크기 편차가 커져서 더 심해진다.

## 결정
1. **분산 식(묶음 추출)을 채택한다.** 집계에 더해지는 숫자 하나로 구현된다
2. **화면 기본 단위는 1분으로 한다.** 1분에서는 추정만으로도 적중률 91.9~94.7%다
3. **5분 이상 집계의 오차 범위는 수면 재생 확정값에서 `Σ A²`를 가져와 계산한다** (ADR-0014 1단계와 연결).
   밤의 재계산은 전량을 처리하므로 칸마다 묶음 크기 제곱합을 **정확히** 낼 수 있다.
   오늘의 구간은 어제의 `Σ A²` 모양에 오늘의 추정 총량을 맞춰 쓴다
   → 위 표의 '정답 분산' 쪽에 가까워진다. 이것이 수면 재생이 정확도에도 쓰이는 두 번째 길이다
4. **기준 ③은 기획서 갱신을 요청한다.** 아래 중 하나로 바꾸는 것을 제안한다
   - (가) `통과 10% 이상에서 5분 단위 조회수 오차 8% 이내` (실측 7.2%에 여유를 둔 값)
   - (나) `통과 40% 이상에서 5분 단위 3% 이내` (원래 숫자를 지키고 조건을 바꿈)
   - (다) `통과 10% 이상에서 30분 단위 3% 이내` (창을 늘림. 여러 시간으로 재확인 필요)
   (가)를 권한다. H2의 이름이 '정직한 정확도'이므로, 못 지킬 숫자를 목표로 두는 것보다
   실제로 지킬 수 있는 숫자를 적고 오차 범위를 함께 띄우는 쪽이 가설의 뜻에 맞다

## 화면에 띄울 값의 크기 (참고)
통과 10% / 1분 칸에서 평균 상대 반폭은 **49%**다 (5분은 74%).
즉 폭증 중 범주·분 단위 화면은 '±50%'를 달고 나온다. 이것이 ADR-0010이 말한
"칸 단위로 2% 정확도는 불가능"의 다른 표현이다. 총량(창 전체)은 같은 조건에서 ±9.7%다.

## 파이프라인에 넣고 확인 (2026-10-19)
구현한 곳
- `main_job.py`: 거르기 단계가 `heavy` 여부도 내보내고, `to_record`를 상태 있는 `ToRecord(MapFunction)`으로
  바꿔 `open()`에서 `ClusterIndex`를 만든다. 흔들림 합은 메인 경로에서 쓰이지 않던 슬롯(가중 매출)에 넣었다
  → `merge`가 이미 그 자리를 더하므로 2단계 집계 구조를 바꾸지 않았다
- `init.sql`: `agg_minute_q` / `agg_minute` / `agg_minute_mv`에 `var_sum Float64`,
  그리고 화면용 `agg_minute_shown` 뷰 (est_count, lo, hi, half_width, rel_half_width)

실제 경로로 확인 (11/17 14:00~14:06 46,564건, 조회 10% 고정, `tools/verify_clickhouse.py shed`)

| 항목 | 값 |
| --- | --- |
| 실제 통과율 | 10.05% (신호 10%) |
| 반폭이 0인 칸 | 0개 (= `var_sum`이 실제로 채워졌다) |
| 평균 상대 반폭 | 46.1% (오프라인 모형 49.0%) |
| 실제 100건 이상인 칸 | 50개, ClickHouse 누락 0 |
| 적중률 | 88.0% (44/50) |

평균 상대 반폭이 오프라인 측정과 거의 같다 → **Flink 구현이 오프라인 모형과 같은 값을 낸다.**
적중률 88.0%는 칸이 50개뿐이라 ±4%p쯤 흔들린다 (오프라인 92.5%와 구별되지 않는다).
적중률의 기준값은 칸이 603개인 오프라인 측정(위 표)을 쓰고, 이 수치는 '구현이 붙었다'는 확인으로만 쓴다.

### 만들다가 찾은 것
- `ClusterIndex`가 '분이 바뀌면 상태를 다 비우기'로 되어 있었다. 조회·장바구니 토픽을 합친 흐름에서는
  분이 뒤섞여 들어와 상태가 계속 날아간다 → 창을 열쇠에 넣고 오래된 분만 치우도록 바꿨다
- `init.sql`은 `CREATE TABLE IF NOT EXISTS`이고 ClickHouse 이미지가 익명 볼륨을 쓴다.
  **열을 늘려도 기존 DB에는 반영되지 않는다** → 개발 중에는 `docker compose rm -sfv clickhouse` 후 다시 띄우고,
  데이터가 쌓인 뒤에는 `ALTER TABLE ... ADD COLUMN`을 써야 한다
